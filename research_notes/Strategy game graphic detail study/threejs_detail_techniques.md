# Fine visual detail in a three.js (r187, WebGLRenderer) scene — techniques, maturity and measured cost, November 2026

Research date: 26 Nov 2026. Method: primary pages fetched directly (three.js release notes via the GitHub API, migration guide, docs, example sources at the `r187` tag or `dev`, pull requests, library READMEs, npm registry, forum threads). The shared web-search budget for this session ran out after five searches, so everything after the first section rests on pages whose URLs were already known; topics that needed discovery by search (WebGL grass benchmarks, depth-foam tutorials, integrated-GPU budgets, Codrops case studies, which returned HTTP 403) are listed under Gaps. This file does not repeat the earlier notes in `research_notes/Strategy game visual craft study/web_graphics_techniques.md` (renderer choice, post-processing basics, AVIF/KTX2, quality tiers); it re-checks them where something may have changed and otherwise adds recipe-level detail.

Status labels used in the findings: **[DOC]** = a documented, working example or library exists and was read; **[MEASURED]** = a published number; **[RULE]** = a published rule of thumb, not a measurement. Everything under "Inferences" is my own reasoning and is untested.

Cost notation where no millisecond figure exists: "+N scene renders" (the scene is drawn again into a render target), "+N fullscreen passes" (one fragment-shader fill of a target), and "taps" (texture fetches per pixel).

## 1. Current state: newest release, what changed r182 → r187 for visual detail, WebGPU status and coverage, benchmarks, migration cost, and whether "stay on WebGLRenderer" still holds

### Takeaway
r187 (30 Oct 2026, npm `three@0.187.0`) is still the newest release and the manual still calls WebGPURenderer "experimental" and WebGLRenderer "the recommended choice for pure WebGL 2 applications", so the advice to stay on WebGLRenderer is unchanged. Between r182 and r187 WebGLRenderer itself gained most of what a detail upgrade needs: rewritten soft shadows, an HDR output buffer with `setEffects()`, a baked light-probe grid, `SunLight` cascades, procedural clouds in `Sky`, cheaper bloom, new physical-material lobes, and an opt-in TSL compatibility layer.

The built-in HDR path (`outputBufferType` + `setEffects`)
- [DOC] Usage: `new WebGLRenderer({ outputBufferType: HalfFloatType }); renderer.setEffects([ taaPass, bloomPass ]); renderer.render( scene, camera );`; effects are only allowed when `outputBufferType` is not `UnsignedByteType`; a redundant `OutputPass` triggers a warning; passes no longer need manual resizing — [PR #32461](https://github.com/mrdoob/three.js/pull/32461)
- mrdoob in the same PR called `setEffects()` "experimental, I'm going to see how much code its needed to get bloom in VR, may revert this"; Mugen87: "The double pass approach is quite noticeable performance-wise" and the inline approach should stay the default "for backwards-compatibility reasons"; a stated downside is that specific materials (e.g. `MeshNormalMaterial`) can no longer be rendered without tone mapping — [PR #32461](https://github.com/mrdoob/three.js/pull/32461)

TSL on WebGLRenderer (the compatibility layer)
- [DOC] Opt in with `renderer.setNodesHandler( new WebGLNodesHandler() )`; merged 14 Mar 2026 for r184. Stated aim: "help enable a transition path and ease users into WebGPURenderer", covering "the 90% use cases" of `onBeforeCompile`; "compatibility" signals WebGLRenderer "will not be a TSL-first renderer" — [PR #32851](https://github.com/mrdoob/three.js/pull/32851)
- Supported: built-in lighting, shadows, skinning, instancing, batching, fog. Unsupported: VSM shadows, MRT nodes, storage textures, transmissive node materials, sharing geometry between `InstancedMesh`es that use node materials, sharing node materials between `SkinnedMesh`es. Known costs: instanced meshes render incorrectly for one frame, PMREM textures are generated twice with environment lighting, and gkjohnson: "it's not so performant in WebGL" — [PR #32851](https://github.com/mrdoob/three.js/pull/32851)
- The r187 source comments repeat the limits ("VSM shadows not supported", "MRT not supported", "Transmission not supported", "WebGPU postprocessing stack not supported", "Fog / environment do not automatically update - must call \"dispose\"") — [WebGLNodesHandler.js at r187](https://raw.githubusercontent.com/mrdoob/three.js/r187/examples/jsm/tsl/WebGLNodesHandler.js)

Benchmarks against WebGLRenderer
- [MEASURED] r183, Chrome 148, RTX 4090 laptop, 4,000 meshes / ~8M triangles: WebGLRenderer 4.5 ms CPU per render and 32 ms cold first frame; WebGPURenderer on WebGPU 9.7 ms and 167 ms; WebGPURenderer with `forceWebGL` 10.3 ms and 344 ms. Four posts, no maintainer reply, no later-release numbers; a community reply advises staying on WebGLRenderer unless WebGPU-specific features are needed — [three.js forum, 29–30 May 2026](https://discourse.threejs.org/t/webgpurenderer-2x-slower-cpu-and-5-10x-slower-first-frame-than-webglrenderer-on-many-mesh-scenes-r183-same-on-both-backends/91904)
- [MEASURED] Issue #30560 (per-object UBO overhead) is still open with labels "High priority" and "Needs Investigation". Mugen87, Jan 2026: ~12 FPS (WebGPURenderer on WebGL 2) vs 60 FPS (WebGLRenderer) in Chrome, 19 vs 57 on a Pixel 8a. Latest data point, 15 Sep 2026 on r186: the WebGL 2 fallback had about 31% more CPU `render()` time (2.88 ms vs 2.20 ms) and about 80% more GL calls (~2350 vs ~1300, mostly `bufferSubData` and `bindBuffer`). No fix merged — [three.js issue #30560](https://github.com/mrdoob/three.js/issues/30560)
- [MEASURED] GPU-bound instanced case, three 0.186.1, RTX 5070 Ti, Chromium 155, 1280×720, DPR 1: 100,000 instances of a 6,056-triangle plant (about 605.6M triangles) ran at 20.26 FPS on classic WebGL, 20.15 on native WebGPU and 20.24 on node WebGL 2; 1k and 10k instances were all capped at 59.99 FPS. ### Inferences
- The advice has not changed and the evidence for it is slightly stronger: the only measured cases where the new renderer matches the old one are GPU-bound instanced scenes; CPU-bound many-object scenes still pay 30%–130% more CPU; the UBO issue is open; the manual wording is unchanged. A game with four procedural scenes, custom `ShaderMaterial`s and a `ShaderPass` chain would have to rewrite all of them for no feature it strictly needs.
- The things a detail upgrade would actually want from the node stack are TRAA, SSGI, compute particles/cloth and instanced skinning (all `webgpu_*` only, see later sections). Each has a WebGL substitute that is good enough for a dark, misty, stylised look: SMAA or MSAA, a baked probe grid plus AO, CPU or GPGPU particles, and rigid-part or morph instancing.
- `setEffects()` is not worth adopting yet for a project that already has a working EffectComposer chain: its author called it experimental, a maintainer flagged its double-pass cost, and the examples have not been migrated. Its one attraction on r187 is `needsDepthTexture`, which hands passes a scene depth texture without a separate pre-pass.
- `WebGLNodesHandler` is a reasonable way to write a *new* shader once (e.g. a triplanar rock material) so it survives a later migration, but with documented one-frame instancing glitches, doubled PMREM generation and "not so performant in WebGL", it should not carry hot-path materials such as terrain or instanced crowds.
- Upgrade risk to schedule for: r188 changes ambient/hemisphere lighting and AO strength, which will shift a carefully tuned low-key look; pmndrs `postprocessing` and `three-good-godrays` both stop at r187 today.

### Gaps
- No maintainer statement on when "experimental" will be dropped, and no fix timeline for #30560.
- No three.js WebGPU-vs-WebGL benchmark on an integrated GPU was found; all published numbers are from RTX 4090/5070 Ti or Apple silicon.
- Firefox release notes were not checked directly; Linux/Android status rests on the gpuweb wiki (2 Oct 2026) and caniuse.
- The exact compatibility of arbitrary addon passes (`ShaderPass`, `UnrealBloomPass`, `GTAOPass`) inside `setEffects()` is not documented in the PR page read.

## 2. Lighting: environment maps and PMREM, procedural sky, light probes, baked lightmaps and AO, in-browser bakers, cheap rim/hemisphere setups

### Takeaway
The WebGL route to believable indirect light in r187 is three stacked, cheap layers: a PMREM environment generated from the procedural `Sky` (now with clouds), a baked `LightProbeGridWebGL` volume for position-dependent diffuse bounce (7 texture fetches per fragment, baked incrementally at load), and baked or screen-space AO. In-browser lightmap bakers exist but are either R3F-only and early-stage or have moved to WebGPU.

### Cited Findings

Environment and sky
- [DOC] `Sky` (WebGLRenderer only; `SkyMesh` for WebGPU) is the Preetham analytic skydome; the docs recommend hiding the sun disc while rendering the environment map: `sky.material.uniforms.showSunDisc.value = false` before, `true` after — [Sky docs](https://threejs.org/docs/pages/Sky.html)
- `Sky` gained procedural clouds in r183 (#32682) and "more realistic clouds" in r186 (#33942); r186 removed the `up` uniform. (The earlier notes dated the clouds to r186; r183 is when they first appeared.) — [r183 notes](https://github.com/mrdoob/three.js/releases/tag/r183), [r186 notes](https://github.com/mrdoob/three.js/releases/tag/r186)
- PMREM changed appearance twice in the period: spiral blur replaced the separable blur (r186, #32367) and the CubeUV atlas was replaced by cube render targets (r187, #34585), with "Restore minimal roughness, improve roughness ramp" (#34645) — [r186 notes](https://github.com/mrdoob/three.js/releases/tag/r186), [r187 notes](https://github.com/mrdoob/three.js/releases/tag/r187)
- Since r183 `MeshLambertMaterial` and `MeshPhongMaterial` accept `scene.environment` IBL — [r183 notes](https://github.com/mrdoob/three.js/releases/tag/r183)
- `MeshPhysicalMaterial` docs: "For best results, always specify an environment map when using this material." — [MeshPhysicalMaterial docs](https://threejs.org/docs/pages/MeshPhysicalMaterial.html)

Light-probe grid (new in r184, WebGL version)
- [DOC] `LightProbeGridWebGL` is "A 3D grid of L2 Spherical Harmonic irradiance probes that provides position-dependent diffuse global illumination"; import from `three/addons/lighting/LightProbeGridWebGL.js`; constructor `( width, height, depth, widthProbes, heightProbes, depthProbes )`; `bake( renderer, scene, { cubemapSize = 8, near = 0.1, far = 100, bounces = 0, start, count, pass } )`; "cubemap rendering, SH projection, and texture packing all happen on the GPU with zero CPU readback"; overlapping grids are resolved by `priority` — [LightProbeGridWebGL docs](https://threejs.org/docs/pages/LightProbeGridWebGL.html)
- Storage and shading cost: one RGBA 3D texture atlas with seven SH sub-volumes, hardware trilinear filtered; the L2 evaluation is "7 `texture()` calls + 9 multiply-adds" per fragment inside a probe volume (an estimate pasted by the PR author, as is "about 24 KB for a 6×6×6 grid"); the author notes "light leaking is hard to solve"; no bake time or FPS was reported ("Performance seems pretty good") — [PR #33125](https://github.com/mrdoob/three.js/pull/33125)
- [DOC] The Sponza example uses a 23.3 × 12.8 × 10.5 volume with 10 × 7 × 7 probes, `cubemapSize: 32`, bounces 1 (GUI 0–2), and bakes incrementally at "a few probes per frame" (`count = Math.min( 4, … )`), restarting the bake whenever the light or shadow settings change; it lights with `SunLight` (2048 shadow map), ACES tone mapping, DPR capped at 1.5, and no post-processing — [webgl_lightprobes_sponza source](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/webgl_lightprobes_sponza.html)
- Incremental baking rules: ranged `start`/`count` calls require `bounces: 0`; for bounces, finish pass 0 over the whole grid and then repeat with `pass: 1`; shadow-casting `SunLight`s are temporarily replaced with directional lights during a bake — [LightProbeGridWebGL docs](https://threejs.org/docs/pages/LightProbeGridWebGL.html)
- r187: "Batch probe capture with ArrayCamera for ~4x faster bakes" (#34909), "Faster multi-bounce" (#35145), "Only sample the last grid that contains the fragment" (#34798) — [r187 notes](https://github.com/mrdoob/three.js/releases/tag/r187)
- Official examples: `webgl_lightprobes`, `webgl_lightprobes_complex`, `webgl_lightprobes_sponza`; also the older `webgl_simple_gi` and `webgl_lights_hemisphere` — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)

Baked lightmaps and in-browser bakers
- [DOC] `ProgressiveLightMap` (WebGLRenderer only; `ProgressiveLightMapGPU.js` for WebGPU): "construct a `ProgressiveLightMap` object, `plmap.addObjectsToLightMap(object)` an array of semi-static objects and lights … then call `plmap.update(camera)` every frame to begin accumulating lighting samples"; lightmap side defaults to 1024; `update( camera, blendWindow = 100, blurEdges = true )`; it rewrites the objects' `uv1`; example `webgl_shadowmap_progressive` — [ProgressiveLightMap docs](https://threejs.org/docs/pages/ProgressiveLightMap.html), [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)
- pmndrs `react-three-lightmap` (159 stars; MIT; only version referenced is v0.0.8): "In-browser lightmap and ambient occlusion (AO map) baker for react-three-fiber and ThreeJS"; bakes on a hidden canvas with its own WebGL context; "currently the lightmap is indirect-only"; denoising is on the wishlist — [react-three-lightmap](https://github.com/pmndrs/react-three-lightmap)
- `three-gpu-pathtracer` (2.1k stars, MIT): the current README says "The project requires WebGPU", shows only `import { WebGPUPathTracer } from 'three-gpu-pathtracer/webgpu'`, and warns "The WebGPU path tracer is not yet stable and relies on three-mesh-bvh APIs that may change between releases." It lists no lightmap or AO baking feature — [three-gpu-pathtracer README](https://raw.githubusercontent.com/gkjohnson/three-gpu-pathtracer/main/README.md)
- The npm package tells a slightly different story: latest `0.0.28` (2 Nov 2026) still exports a root entry as well as `./webgpu`, with peers `three >=0.187.0`, `three-mesh-bvh >=0.9.17` and `xatlas-web ^0.1.0` (a UV-unwrapping library) — [npm registry](https://registry.npmjs.org/three-gpu-pathtracer)
- A 2026 procedural driving game credits "a day/night cycle, Northern Lights, planar reflections, IBL" and "moon, IBL and baked AO" — [three.js forum, Jul 2026](https://discourse.threejs.org/t/infinite-procedural-post-apocalyptic-winter-driving-game/93196)

### Inferences
- Recipe for the city diorama and the two battle scenes (untested combination of documented parts): build `Sky` with a low sun and heavy cloud, hide the sun disc, `PMREMGenerator.fromScene()` it once into `scene.environment` with a low `environmentIntensity`; add one `LightProbeGridWebGL` sized to the diorama (for example 8 × 3 × 8 probes, `cubemapSize` 16, one bounce) and bake it 4 probes per frame behind the scene transition; keep one shadowed key light. Per-frame cost is the 7 extra fetches on lit fragments; the bake is a one-off of `probes × 6` tiny renders per pass.
- Firelight is the natural payoff of the probe grid: bake the grid with braziers and campfires lit so warm bounce reaches nearby walls and ground without any real-time point-light shadows; re-bake a few probes per frame only when a fire is lit or put out.
- Because all geometry is procedural and has no lightmap UVs, per-vertex baked AO stored in vertex colour is the cheapest "baked lighting": compute it at build time and multiply it in. No documented three.js helper for this was verified in this session; it is my inference from general practice. `ProgressiveLightMap` is the documented alternative but needs unwrapped `uv1` and accumulates over about 100 frames.
- Cheap rim light for dark silhouettes: a back/side `DirectionalLight` without shadows plus a low `HemisphereLight` is the standard documented setup; a Fresnel-style rim term added in the fragment shader costs a few instructions. Note that from r188 the hemisphere light will also add specular, so intensities tuned on r187 will need lowering.
- The `xatlas-web` peer dependency suggests `three-gpu-pathtracer` still has an unwrap-and-bake path somewhere, but with the README now describing only an unstable WebGPU tracer it should not be planned around.

### Gaps
- No bake-time or runtime measurements for `LightProbeGridWebGL` were published in the PR, docs or examples.
- Whether the root (non-WebGPU) entry of `three-gpu-pathtracer` 0.0.28 still ships a working WebGL2 path tracer was not verified; README and package metadata disagree.
- No maintained, vanilla-three.js (non-React) lightmap baker for WebGL was found.
- No documented three.js utility for per-vertex AO baking of procedural geometry was verified (search budget exhausted).

## 3. Shadows: PCSS, VSM, contact shadows, cascades, fitting a frustum to a diorama, resolution and cost

### Takeaway
Since r182 the default `PCFShadowMap` is already a soft, noise-rotated filter (5 hardware-filtered taps ≈ 20 effective taps), which makes it the right baseline; VSM remains for wide blur on directional/spot lights only, PCSS exists as an official example that patches a shader chunk at 51 depth taps per fragment, and blurred contact shadows cost one small extra scene render plus four 512² blur passes and can be frozen for static dioramas.

### Cited Findings

What the r182 rewrite did
- PR #32303 (merged 23 Nov 2025): native depth textures replace RGBA depth packing; PCF uses `sampler2DShadow`/`samplerCubeShadow`; "Vogel disk sampling with per-pixel interleaved gradient noise"; 5 samples with hardware 4-tap filtering give about 20 filtered taps; "Removed `PCFSoftShadowMap` as the new `PCFShadowMap` is already soft"; point lights render to a new `CubeDepthTexture`; VSM is skipped for point lights with a console warning — [PR #32303](https://github.com/mrdoob/three.js/pull/32303)
- [MEASURED] Same PR: a test scene "now renders 2x faster on a Pixel 3a (8fps vs 18fps)" (single device) — [PR #32303](https://github.com/mrdoob/three.js/pull/32303)
- r187 shader, PCF branch: `vec2 radius = shadowRadius * texelSize;`, five `texture()` calls on a `sampler2DShadow` at Vogel-disk offsets rotated by interleaved gradient noise on `gl_FragCoord.xy`, averaged with `* 0.2` — [shadowmap_pars_fragment at r187](https://raw.githubusercontent.com/mrdoob/three.js/r187/src/renderers/shaders/ShaderChunk/shadowmap_pars_fragment.glsl.js)
- r187 shader, VSM branch: one `texture2D(...).rg` read (mean and standard deviation), Chebyshev bound `p_max = variance / (variance + d*d)`, light-bleed reduction `clamp( ( p_max - 0.3 ) / 0.65, 0.0, 1.0 )` — [shadowmap_pars_fragment at r187](https://raw.githubusercontent.com/mrdoob/three.js/r187/src/renderers/shaders/ShaderChunk/shadowmap_pars_fragment.glsl.js)
- Maintainer view on keeping VSM: it "can blur the shadow map as a whole which a great quality advantage over PCF" — [PR #32181](https://github.com/mrdoob/three.js/pull/32181)
- Later fixes: reversed-depth shadow bias (r183 #32770, r187 #34892), "Implement normal bias fallback" (r184 #33391), "Fix point light shadow seams" (r187 #35267) — [r183 notes](https://github.com/mrdoob/three.js/releases/tag/r183), [r184 notes](https://github.com/mrdoob/three.js/releases/tag/r184), [r187 notes](https://github.com/mrdoob/three.js/releases/tag/r187)

Per-light controls
- `LightShadow` defaults: `mapSize` (512, 512), "Higher values give better quality shadows at the cost of computation time. Values must be powers of two."; `radius` 1 ("values greater than 1 will blur the edges … High values will cause unwanted banding effects"; no effect with `BasicShadowMap`); `blurSamples` 8 ("when blurring a VSM shadow map"); `bias` 0 ("Very tiny adjustments here (in the order of `0.0001`) may help"); `normalBias` 0 (helps "where light shines onto geometry at a shallow angle. The cost is that shadows may appear distorted."); `intensity` 1; `autoUpdate` true ("If you do not require dynamic lighting / shadows, you may set this to `false`") with `needsUpdate` to refresh once — [LightShadow docs](https://threejs.org/docs/pages/LightShadow.html)

PCSS (contact-hardening soft shadows)
- [DOC] `webgl_shadowmap_pcss` patches `THREE.ShaderChunk.shadowmap_pars_fragment` with two exact-string `replace()` calls before the renderer is created, and sets `renderer.shadowMap.type = THREE.BasicShadowMap` because "PCSS requires reading raw depth values". Constants: `LIGHT_WORLD_SIZE 0.005`, `LIGHT_FRUSTUM_WIDTH 3.75`, `NEAR_PLANE 9.5`, `NUM_SAMPLES 17`, `NUM_RINGS 11`; 17 blocker-search taps plus 2 × 17 PCF taps = 51 depth reads per shadowed fragment; shadow map 1024² — [webgl_shadowmap_pcss source](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/webgl_shadowmap_pcss.html)
- [DOC] drei `SoftShadows` (docs for drei v10.7.9): "Injects percent closer soft shadows (pcss) into threes shader chunk"; props `size` 25, `samples` 10, `focus` 0; "Mounting and unmounting this component will lead to all shaders being be re-compiled" — [drei docs: SoftShadows](https://drei.docs.pmnd.rs/shaders/soft-shadows)

Contact shadows
- [DOC] `webgl_shadow_contact`: an orthographic camera at ground level looking up (`rotation.x = Math.PI / 2`) with near 0 and far `CAMERA_HEIGHT = 0.3`, frustum equal to the 2.5 × 2.5 ground plane; the scene is drawn with an overridden `MeshDepthMaterial` whose fragment output is `vec4( vec3( 0.0 ), ( 1.0 - fragCoordZ ) * darkness )` into a 512² target; two separable blur rounds (`blur` 3.5, then `blur * 0.4` "to reduce the artifacts") through a second 512² target; the result is drawn on a plane. Per frame: +1 scene render into 512² and +4 quad passes at 512² — [webgl_shadow_contact source](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/webgl_shadow_contact.html)
- drei `ContactShadows`: "Since this is a rather expensive effect you can limit the amount of frames it renders when your objects are static"; `frames={1}` renders once — [drei docs: ContactShadows](https://drei.docs.pmnd.rs/staging/contact-shadows)

Cascades
- `SunLight` PR: cascades are "fitted to the view frustum every frame", texel-snapped, blended at boundaries and faded at the maximum distance; 1024² per cascade by default; the only setting needed is `shadow.camera.far`; the PR began with four cascades and r186 shipped "Reduce cascade count to 2"; Mugen87 on the older `CSM` addon: it patches chunks through `onBeforeCompile()`, "no ideal approach" — [PR #34221](https://github.com/mrdoob/three.js/pull/34221), [r186 notes](https://github.com/mrdoob/three.js/releases/tag/r186)
- (From the earlier notes, still current) the `SunLight` docs say it is "not a good fit for small, bounded scenes like dioramas" — [SunLight docs](https://threejs.org/docs/pages/SunLight.html)

Cost model and field practice
- [RULE] "For each omni light that casts shadow, the scene must be rendered 6 times into a shadow map." — [PlayCanvas optimization guidelines](https://developer.playcanvas.com/user-manual/optimization/guidelines/)
- A 2026 three.js game limits shadow-pass geometry by partitioning: "towns cut into 60 m blocks so only the useful part goes into the shadow pass" — [three.js forum, Nov 2026](https://discourse.threejs.org/t/tides-of-fortune-an-open-world-pirate-game-in-three-js-with-zero-asset-files/96867)
- Side effect of the r182 rewrite for libraries that read the shadow map: with `PCFShadowMap`, `three-good-godrays` "copies the shadow map depth data to a separate texture each frame"; `BasicShadowMap` and `VSMShadowMap` are read directly — [three-good-godrays](https://github.com/Ameobea/three-good-godrays)

### Inferences
- Fitting a frustum to a diorama (arithmetic, not from a source): shadow sharpness is `frustum width ÷ mapSize` world units per texel. A 40-unit-wide city diorama in a 2048² map is about 2 cm per texel at 1 unit = 1 m; the same map stretched over a 400-unit frustum is 20 cm per texel and looks blurry however it is filtered. Set the directional light's orthographic `left/right/top/bottom` to the diorama's bounds projected into light space, pull `near`/`far` tight (depth precision and bias both improve), and for the tilted campaign map fit to the visible map rectangle rather than the whole map.
- Static scenes should not pay for shadows every frame: set `light.shadow.autoUpdate = false` and raise `needsUpdate` only when something that casts moves. For the diorama and campaign map this turns the shadow pass into an occasional cost; marching armies can use blurred blob shadows or a frozen contact-shadow texture instead of forcing updates.
- Suggested default per scene: `PCFShadowMap` with `radius` 2–4 on a tightly fitted 2048² map (1024² on the low tier). Use VSM only where a deliberately wide, soft, misty shadow is wanted on a directional or spot light; it cannot be used for point-light fires. PCSS at 51 taps per fragment is a high-tier, close-up-only option (the duel), and because both the official example and drei patch the shader chunk by exact string match, the patch must be re-verified on every three.js upgrade; the r182 rewrite changed the surrounding code.
- For firelight, a shadow-casting `PointLight` is 6 scene renders; one or two at 512² are affordable in the duel, not across a war theater. A `SpotLight` aimed down from the fire, or no shadow at all plus the probe grid's baked bounce, gives most of the look.
- Contact shadows suit the duel (two horses on a ground plane): one 512² depth render of two characters plus four small blur passes is small next to a full shadow map, and gives the grounded look that distance-softened PCF lacks.

### Gaps
- The three.js manual page on shadows returned HTTP 404 at the URL tried, so no official text on frustum fitting is quoted; the fitting advice above is inference.
- No millisecond cost for PCSS, VSM blur or contact shadows on any GPU was found.
- Whether drei `SoftShadows` and the official PCSS example patch cleanly against the r187 chunk text was not verified by running them.

## 4. Ambient occlusion and indirect light: GTAOPass, N8AO, half-resolution SSAO, screen-space GI

### Takeaway
N8AO at half resolution is the only WebGL AO option with published timings (0.70 ms at 1080p in Medium mode on an Apple M5 Max, with half-res giving 2–4×), `GTAOPass` is the in-repo alternative with no published cost, and there is no maintained screen-space GI for WebGLRenderer: `SSGINode` is WebGPU-only, `realism-effects` is reported stale, and the practical WebGL substitute is the baked probe grid from section 2.

### Cited Findings
- [MEASURED] N8AO 2.1 changelog, 1080p, Apple M5 Max: Medium 0.78 → 0.70 ms; Ultra 2.5 → 2.0 ms; Neural-Medium 1.8 → 1.1 ms; Neural-High 2.8 → 1.5 ms; depth-aware half-res upsampling about 0.1 ms. "Half-res mode generally gives a 2x–4x speed boost." — [N8AO README](https://github.com/N8python/n8ao)
- N8AO quality modes: Performance 8 AO samples / 4 denoise (best for "Mobile, low-end iGPUs, laptops"), Low 16/4, Medium 16/8 (default), High 64/8, Ultra 64/16, plus Neural variants (neural denoising off by default). Options: `halfRes`, `screenSpaceRadius` (radius in pixels, 16–64 recommended), `accumulate` (averages while the camera is still, stops after 1024 samples per pixel), `transparencyAware` (transparent objects are rendered twice), `stencil` — [N8AO README](https://github.com/N8python/n8ao)
- N8AO integration and constraints: `N8AOPass` replaces `RenderPass` in three's EffectComposer, `N8AOPostPass` is for pmndrs; hardware antialiasing does not work with AO, SMAA is recommended; WebGL 2 only; r161+ recommended; logarithmic depth and orthographic cameras supported; WebGPU "not yet supported"; 524 stars; latest npm version 2.1.0 — [N8AO README](https://github.com/N8python/n8ao), [npm registry](https://registry.npmjs.org/n8ao)
- Licence conflict: the README states "A CC0 license is used for this project", while earlier npm versions list ISC — [N8AO README](https://github.com/N8python/n8ao), [npm registry](https://registry.npmjs.org/n8ao)
- `GTAOPass`: "provides better quality than SSAOPass but is also more expensive"; constructor `( scene, camera, width, height, parameters, aoParameters, pdParameters )` with width/height default 512; Poisson-denoise defaults `pdSamples` 16, `pdRings` 2, `pdRadiusExponent` 2; `setGBuffer( depthTexture, normalTexture )` accepts external buffers and "If no normal texture is supplied, normals are reconstructed from depth"; `setSceneClipBox( box )` limits AO to a box — [GTAOPass docs](https://threejs.org/docs/pages/GTAOPass.html)
- r187 changed `GTAOPass`: "Remove combined depth and normal texture support" (#34836), "Fix external buffer handling" (#34831) — [r187 notes](https://github.com/mrdoob/three.js/releases/tag/r187)
- WebGL AO examples in the repo: `webgl_postprocessing_gtao`, `webgl_postprocessing_ssao`, `webgl_postprocessing_sao` — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)
- A shipped 2026 three.js r186 game reserves AO for its top tier: "FXAA by default, or SMAA + GTAO in 'Ultra' quality" — [three.js forum, Nov 2026](https://discourse.threejs.org/t/tides-of-fortune-an-open-world-pirate-game-in-three-js-with-zero-asset-files/96867)
- From r188, multi-bounce AO "weakens occlusion on bright and metallic surfaces"; compensate with stronger GTAO/SSAO or a re-baked `aoMap` — [Migration Guide](https://github.com/mrdoob/three.js/wiki/Migration-Guide)
- Screen-space GI: only `webgpu_postprocessing_ssgi` and `webgpu_postprocessing_ssgi_ballpool` exist — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)
- `realism-effects` (the WebGL SSGI/SSR/motion-blur library): a forum thread reports the repository "has not been updated for two years" and "is not compatible with current threejs version" — [three.js forum (search snippet only)](https://discourse.threejs.org/t/substitutes-for-realism-effects/86443)
- N8GI (N8python, 71 stars, no releases, no licence shown): "A heavy and visually pleasing implementation of world-space global illumination with an emphasis on temporal stability and artist control"; file names indicate voxelisation in a worker plus a Poisson blur — [N8GI](https://github.com/N8python/N8GI)

### Inferences
- For this project AO earns its cost only in the close scenes (city diorama, duel) where contact darkening under eaves, between armour plates and where hooves meet ground sells detail. Recommended: N8AO, `halfRes = true`, "Performance" preset on integrated GPUs, "Low"/"Medium" on discrete; `screenSpaceRadius` on so the look is stable across zoom. On the campaign map, bake cavity into the terrain shader from the heightmap instead.
- Scaling the one published number is guesswork: an Apple M5 Max is perhaps 10–30× faster than a UHD-class integrated GPU, so 0.7 ms could become anything from several milliseconds upward at 1080p full resolution. Half resolution and the 8-sample preset are therefore the starting point, and AO should sit behind the quality tier switch.
- N8AO's `accumulate` suits a strategy game well: the camera is often still, so AO can refine over idle frames at no extra per-frame cost.
- AO and MSAA do not mix (N8AO's own note), so enabling AO implies SMAA or FXAA for anti-aliasing, which in turn affects alpha-to-coverage foliage (section 8).
- A dark art direction hides AO: in already-low-key frames screen-space AO mostly darkens what is already dark. Check the effect with the AO debug output before paying for it; a baked probe grid adding *light* variation may do more for depth than AO removing it.

### Gaps
- No AO timing on any integrated GPU (Intel UHD/Iris Xe, AMD Radeon integrated) was found; N8AO publishes Apple M5 Max only and `GTAOPass`/`SSAOPass` publish nothing.
- The `realism-effects` status comes from a search snippet; the repository itself was not opened.
- N8GI's requirements, licence and cost are undocumented on its repository page.

## 5. Materials: MeshPhysicalMaterial features, detail normals, triplanar, procedural and canvas textures, edge wear and dirt, and how to extend built-in materials

### Takeaway
`MeshPhysicalMaterial` in r187 covers cloth (sheen), brushed and hammered metal (anisotropy), lacquer and wet surfaces (clearcoat), patina (iridescence) and dusty matte surfaces (the new EON `diffuseRoughness`), each off by default and costing only when enabled; detail normals, triplanar mapping and curvature-based wear have no built-in WebGL support and must be injected with `onBeforeCompile`, with `three-custom-shader-material`, or with TSL through the compatibility layer.

### Cited Findings

Built-in physical features
- Cost statement: "`MeshPhysicalMaterial` has a higher performance cost, per pixel, than other three.js materials. Most effects are disabled by default, and add cost as they are enabled." — [MeshPhysicalMaterial docs](https://threejs.org/docs/pages/MeshPhysicalMaterial.html)
- Sheen ("Used for cloth and fabric"): `sheen` 0–1, `sheenColor`, `sheenRoughness` (default 1), plus colour and roughness maps. Anisotropy ("Simulates brushed metals"): `anisotropy` 0–1, `anisotropyRotation` in radians, `anisotropyMap` (RG direction, B strength). Clearcoat ("car paint, carbon fiber, and wet surfaces"): `clearcoat`, `clearcoatRoughness`, and an independent `clearcoatNormalMap` with `clearcoatNormalScale`. Iridescence: `iridescence`, `iridescenceIOR` 1.3, `iridescenceThicknessMinimum` 100 nm and `iridescenceThicknessMaximum` 400 nm (the `…Range` property is deprecated since r187) — [MeshPhysicalMaterial docs](https://threejs.org/docs/pages/MeshPhysicalMaterial.html)
- New in r187: `diffuseRoughness` 0–1 — "`0.0` uses Lambertian reflection. Values above `0.0` use the EON energy-preserving rough diffuse model" — with `diffuseRoughnessMap`; new in r186: `retroreflectivity` 0–1 — [MeshPhysicalMaterial docs](https://threejs.org/docs/pages/MeshPhysicalMaterial.html), [r187 notes](https://github.com/mrdoob/three.js/releases/tag/r187)
- Sheen was reworked twice (r182 "Improve Sheen energy conservation and analytic approximation"; r186 "Improve energy conservation for diffuse and sheen lighting"), so sheen tuned on older versions looks different — [r182 notes](https://github.com/mrdoob/three.js/releases/tag/r182), [r186 notes](https://github.com/mrdoob/three.js/releases/tag/r186)
- [DOC] WebGL examples: `webgl_materials_physical_clearcoat`, `webgl_loader_gltf_sheen`, `webgl_loader_gltf_anisotropy`, `webgl_loader_gltf_iridescence`, `webgl_materials_bumpmap`, `webgl_materials_normalmap`, `webgl_materials_displacementmap`, `webgl_materials_texture_canvas`, `webgl_materials_modified` — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)
- r184: WebGLRenderer "Add support for packed normal maps" (#33055) — [r184 notes](https://github.com/mrdoob/three.js/releases/tag/r184)
- `Material.dithering`: "Whether to apply dithering to the color to remove the appearance of banding." (default false); `Material.vertexColors` supports RGB and RGBA attributes — [Material docs](https://threejs.org/docs/pages/Material.html)

Three ways to extend a built-in material
- `onBeforeCompile( shaderobject, renderer )`: "executed immediately before the shader program is compiled … Useful for the modification of built-in materials. This method can only be used when rendering with WebGLRenderer."; `customProgramCacheKey()` lets three "reuse a cached shader or recompile the shader for this material as needed" — [Material docs](https://threejs.org/docs/pages/Material.html)
- `three-custom-shader-material` (1.4k stars, MIT, latest npm 6.4.0): wraps a base material class and exposes outputs `csm_Position`, `csm_Normal`, `csm_DiffuseColor`, `csm_FragColor`, `csm_Roughness`, `csm_Metalness`, `csm_AO`, `csm_Emissive`, `csm_FragNormal`, `csm_Clearcoat*`, `csm_Iridescence`, `csm_DepthAlpha` (for a custom depth material) and `csm_UnlitFac`; vanilla import `three-custom-shader-material/vanilla`; caveats: `csm_Roughness`/`csm_Metalness`/`csm_AO` "require the matching map on the base material", identifiers are not scoped when chaining, bump mapping was removed in v6.4.0 in favour of `csm_FragNormal`; no WebGPU/TSL mention — [THREE-CustomShaderMaterial](https://github.com/FarazzShaikh/THREE-CustomShaderMaterial), [npm registry](https://registry.npmjs.org/three-custom-shader-material)
- TSL node materials on WebGLRenderer via `WebGLNodesHandler` (limits in section 1); official examples `webgl_tsl_shadowmap`, `webgl_tsl_skinning`, `webgl_tsl_clearcoat`, `webgl_tsl_instancing` — [PR #32851](https://github.com/mrdoob/three.js/pull/32851), [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)

Procedural textures in practice
- A 2026 r186 game ships with no asset files: "Ships, rigging, islands, towns, characters, textures, music and sound are all generated in code at load time"; "the hull shader recolours the paint and trim areas, keeping the baked shading, wear and damage"; generation is time-sliced — the build loop "pauses as soon as it uses up its 1.5 ms per frame"; the whole game is "a single ~2 MB HTML file (700 kB compressed)" — [three.js forum, Nov 2026](https://discourse.threejs.org/t/tides-of-fortune-an-open-world-pirate-game-in-three-js-with-zero-asset-files/96867)

### Inferences
- Material map for the stated art direction (my mapping of documented features to subjects, untested): banners, capes and tents → `sheen` 0.5–1 with a dark, slightly warm `sheenColor` and `sheenRoughness` about 0.5; bronze fittings and blades → `metalness` 1 with `anisotropy` 0.4–0.8 for brushed streaks and a bronze-gold specular from the environment; lacquered armour and wet ground → `clearcoat` with low `clearcoatRoughness`; verdigris or heat tint on bronze → low `iridescence`; plaster, rammed earth and dry dust → `diffuseRoughness` near 1 for the flatter EON falloff. Enable each lobe only on the materials that need it, because every enabled lobe adds per-pixel work and a new shader permutation to compile.
- Detail normal maps: three has one `normalMap` slot (the only second normal slot documented is `clearcoatNormalMap`, which affects the clearcoat layer only). A detail layer therefore needs injected code: sample a small tiling noise-normal at high UV scale, fade it out with distance, and blend it into the normal after `#include <normal_fragment_maps>` (via `onBeforeCompile`) or through `csm_FragNormal`. Cost is one extra fetch near the camera.
- Triplanar mapping for procedural geometry without UVs: three fetches weighted by `abs(normal)` raised to a power, in world or object space. TSL has `triplanarTexture()`; on WebGLRenderer it is hand-written GLSL. It suits cliffs, city walls and rocks; avoid it on the whole terrain (3× the fetches).
- Edge wear and dirt without textures: at geometry-build time compute a per-vertex convexity value (e.g. from the angle between adjacent face normals) and an AO value, store them in two vertex-colour channels, then in the shader raise roughness and lighten/bronze the colour where convexity is high (worn edges) and darken/desaturate where AO is high (grime in recesses), broken up by a noise fetch. This is a standard offline-rendering trick; I found no documented three.js implementation in this session.
- Canvas-generated textures (`CanvasTexture`) are the practical way to get brick courses, wood grain, roof-tile rows, woven cloth and banner emblems for procedural meshes; generate once at load in slices of a few milliseconds per frame (the cited game budgets 1.5 ms per frame), generate mipmaps, set anisotropy, and reuse across instances. Derive a normal map from a canvas height image with a Sobel pass so the same pattern gives relief.
- Choosing between the extension routes: keep existing hot-path `ShaderMaterial`s; use `onBeforeCompile` with `customProgramCacheKey` (or `three-custom-shader-material` for readability) when the goal is "standard PBR lighting, shadows and fog plus one extra term"; reserve TSL-on-WebGL for new, non-instanced hero materials. All three are WebGL-only except TSL.
- In a dark, low-contrast frame, banding in mist gradients is the visible artefact: keep the composer's buffers at half float and turn on `dithering` for large smooth surfaces, or add blue-noise dither in the final grading pass.

### Gaps
- No documented three.js example of detail-normal blending, triplanar mapping on WebGLRenderer, or curvature-driven edge wear was verified (search budget exhausted); the recipes above are inference.
- No published per-lobe cost (sheen, clearcoat, anisotropy, iridescence) in milliseconds was found.
- `three-custom-shader-material`'s supported three.js range and last release date were not visible in the pages read.

## 6. Terrain: splat and height-blended texturing, slope and altitude rules, parallax occlusion mapping, normal detail at close zoom

### Takeaway
Terrain texturing in three.js remains a hand-written shader: the classic height-blend function gives natural material transitions for a few instructions, slope and altitude rules come from the heightmap already in use, and parallax occlusion mapping has no WebGLRenderer example at all in r187 (only a TSL `webgpu_parallax_uv`), so close-zoom relief should come from detail normals and real displacement instead.

### Cited Findings
- [DOC, non-three.js] Height-based blend (Andrey Mishkinis, 16 Jul 2013): `float depth = 0.2; float ma = max(texture1.a + a1, texture2.a + a2) - depth; float b1 = max(texture1.a + a1 - ma, 0); float b2 = max(texture2.a + a2 - ma, 0); return (texture1.rgb * b1 + texture2.rgb * b2) / (b1 + b2);` where each texture's alpha stores a height map and `a1`/`a2` are the splat weights; plain linear blending is "smooth but unnatural", while this lets sand settle into cracks and keeps stone tops clear — [Game Developer: Advanced Terrain Texture Splatting](https://www.gamedeveloper.com/programming/advanced-terrain-texture-splatting)
- No `webgl_materials_parallaxmap` example exists in the current index; the only parallax example is `webgpu_parallax_uv`; the WebGL terrain examples are `webgl_geometry_terrain`, `webgl_geometry_terrain_raycast` and `physics_rapier_terrain`/`physics_ammo_terrain` — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)
- `GLTFLoader` now lists `EXT_materials_bump` among built-in extensions — [GLTFLoader docs](https://threejs.org/docs/pages/GLTFLoader.html)
- Peer-engine signal: the PlayCanvas Editor added parallax occlusion in release 2.32 (22 Sep 2026) — [PlayCanvas blog index](https://blog.playcanvas.com/)
- Field practice, 2026 three.js games: terrain "baked in parallel in Web Workers during loading" with instanced vegetation; and "a low quality terrain further away in the distance, instead of geenrating the chunks and popping them up in place" — [Tides of Fortune thread](https://discourse.threejs.org/t/tides-of-fortune-an-open-world-pirate-game-in-three-js-with-zero-asset-files/96867), [winter driving game thread](https://discourse.threejs.org/t/infinite-procedural-post-apocalyptic-winter-driving-game/93196)
- Sampler budget that bounds a splat shader: `MAX_TEXTURE_IMAGE_UNITS` is ≥16 on 100% of surveyed WebGL 2 devices but ≥24 on only 13% — [Web3D Survey: WebGL 2](https://web3dsurvey.com/webgl2)
- Texture-array examples that avoid the sampler limit: `webgl_texture2darray`, `webgl_texture2darray_compressed`, `webgl_texture2darray_layerupdate`, `webgl_rendertarget_texture2darray` — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)

### Inferences
- Recipe for the campaign map's displaced relief (assembled from the documented blend plus standard rules; untested here): derive slope from the heightmap normal (`1 − normal.y`) and altitude from height; build four weights — lowland soil/grass, rock where slope exceeds a threshold, snow or bare ridge above an altitude band, and wet silt near rivers from the river distance field — perturb each threshold with low-frequency noise so bands are not contour-straight, then combine layers pairwise with the height-blend function using each layer's height in its alpha channel. For a drained, low-key palette the layers can be near-monochrome with the colour variation carried by a single tint texture.
- Store the layers in one `DataArrayTexture` (albedo+height) and optionally a second (normal+roughness): two samplers instead of eight, well inside the 16-unit limit that every surveyed device has, leaving units for shadow maps, the probe atlas and environment.
- Close zoom: add a tiling detail normal that fades in below a camera-distance threshold, and scale its strength by slope so cliffs look fractured and plains stay calm. Since the terrain is already a displaced mesh, increasing tessellation near the camera (or a denser inner patch) gives true silhouette relief, which parallax mapping cannot.
- Parallax occlusion mapping is a poor fit here: it has no maintained WebGL implementation in three.js, costs a ray-march of 8–32 height fetches per pixel on exactly the surfaces that fill the screen at a tilted map angle, and produces wrong silhouettes and shadowing. If a ground close-up needs it (duel arena cobbles), a simple single-step parallax offset costs one extra fetch and is usually enough under mist.
- Tiling repetition across a wide map is the more visible flaw than missing relief: break it with a second sample at a non-integer UV scale, or noise-driven UV offsets, before spending on POM.

### Gaps
- No maintained three.js splat-terrain library beyond `three-landscape` (covered in the earlier notes) was found, and no WebGL POM implementation for current three.js was verified (search budget exhausted).
- No measured cost for 4-layer height-blended splatting on integrated GPUs was found.

## 7. Water: flow maps, depth-based colour and shore foam, planar or screen-space reflections, Gerstner waves, caustics

### Takeaway
three.js ships a flow-mapped water addon (`Water2.js`) whose two-phase scrolling is the recipe to copy for rivers, but it pays two extra scene renders per frame for reflection and refraction; for a campaign map the flow-map idea should be lifted into the river shader without the render targets, with depth-based foam needing a scene depth texture and Gerstner waves reserved for open water.

### Cited Findings

Flow maps
- [DOC] `Water2.js` at r187 (WebGLRenderer only): options `color` 0xFFFFFF, `textureWidth/Height` 512, `flowDirection` (1, 0), `flowSpeed` 0.03, `reflectivity` 0.02, `scale` 1, optional `flowMap` (defines `USE_FLOWMAP`), `normalMap0`/`normalMap1`. Shader: flow direction is `flowMap.rg * 2 - 1`; two normal-map samples are offset by `flowMapOffset0` and `flowMapOffset1`, kept exactly half a cycle apart (`cycle = 0.15`, `halfCycle = 0.075`), and mixed with `flowLerp = abs( halfCycle - offset0 ) / halfCycle` so the reset of one phase is hidden by the other. References cited in the file: Vlachos's SIGGRAPH 2010 water-flow talk — [Water2.js at r187](https://raw.githubusercontent.com/mrdoob/three.js/r187/examples/jsm/objects/Water2.js)
- Cost of `Water2`: `onBeforeRender` hides the water and renders both a `Reflector` and a `Refractor`, i.e. +2 scene renders per frame into 512² targets — [Water2.js at r187](https://raw.githubusercontent.com/mrdoob/three.js/r187/examples/jsm/objects/Water2.js)
- The current examples index (dev) lists `webgl_shaders_ocean`, `webgl_gpgpu_water`, `webgl_mirror` and `webgl_refraction`, but no longer `webgl_water` or `webgl_water_flowmap` — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)

Reflections

Caustics
- [DOC] Maxime Heckel, 23 Jan 2024 (R3F, WebGL): render the refractive mesh's normals from the light's view into a 2000² FBO; in a second 2000² FBO refract the light direction (`refract( lightDir, normal, 1.0 / 1.25 )`) and estimate intensity as the ratio of patch areas before and after refraction using `length( dFdx( p ) ) * length( dFdy( p ) )`; soften with a 16-sample chromatic pass; blend with `CustomBlending`, `OneFactor`/`SrcAlphaFactor`. Stated limits: two large FBOs and a normal pass every frame; depends on tessellation; the plane fit needs an empirical 1.75 scale correction — [Maxime Heckel: Caustics in WebGL](https://blog.maximeheckel.com/posts/caustics-in-webgl/)
- three.js caustics examples are WebGPU-only (`webgpu_caustics`, `webgpu_volume_caustics`) — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)

### Inferences
- Campaign-map rivers (recipe, untested): keep the river as a strip or distance-field mask in the terrain shader. Bake a flow-direction texture once from the river centre-line tangents (RG) and a shore-distance value (B). In the fragment shader use the `Water2` two-phase trick — two samples of a tiling normal/noise texture offset along the flow vector, half a cycle apart, cross-faded by the triangle wave — to perturb the normal and to scroll a foam-streak noise. Cost: 3–4 fetches, no extra scene render.
- Shore foam and depth colour without a depth texture: on a heightmap terrain the water depth is known analytically (`waterLevel − terrainHeight`), so foam where depth is below a noisy threshold and colour graded from silt to dark with depth both come from the heightmap fetch the shader already makes. The depth-buffer method (linearise scene depth behind the water fragment and subtract the fragment's own depth) is only needed where arbitrary meshes — boats, bridge piers, wading horses — intersect the surface, and it requires rendering the opaque scene to a target with a `DepthTexture` first and drawing water afterwards.
- Reflections for a dark, misty look: a full planar `Reflector` (+1 scene render) is hard to justify on the map; the PMREM sky sampled with the perturbed normal and a Fresnel factor gives a convincing sheen for one fetch. In the city close-up, if a moat or pond is a focal element, use a `Reflector` at quarter resolution with a restricted layer set and update it every second frame.
- Gerstner waves (4–8 summed in the vertex shader, normals from analytic derivatives) only pay off on a large open surface seen at a grazing angle — a lake or the Yangtze in the war theater. Rivers at map scale read better with flow-mapped normals than with displacement.
- Caustics: Heckel's method is designed for a hero refractive object and costs two 2000² targets per frame; for shallow river beds a scrolling, flow-distorted caustic texture multiplied into the bed colour where depth is small gives the visual cue for one fetch.
- Wakes, ripples and footprints in water can share one mechanism with ground decals (section 12): draw brush sprites into a persistent render target in map space each frame with a fade, and sample it in the water shader as extra foam and normal disturbance — the approach the cited game describes as "foam wakes drawn into a texture".

### Gaps
- No working three.js tutorial for depth-buffer shore foam was retrieved (the known forum thread has no recipe and the Codrops stylised-water article returned HTTP 403); the depth-difference recipe above is general practice stated as inference.
- Whether `webgl_water` and `webgl_water_flowmap` were deliberately removed from the examples (the addon file itself is present at the r187 tag) was not confirmed from a PR.
- No measured cost of `Reflector`, `Water`, or `Water2` on any GPU was found.

## 8. Vegetation: instanced grass and trees, wind animation, impostors and billboards, alpha-to-coverage and alpha hashing

### Takeaway
Instanced vegetation on WebGLRenderer scales to very large counts on a discrete GPU (100,000 instances of a 6,056-triangle plant still ran at 20 FPS on an RTX 5070 Ti), the official `webgl_batch_lod_bvh` example shows 500,000 `BatchedMesh` instances with five LOD levels and BVH culling, and the newest grass systems are WebGPU-only; for integrated GPUs the budget is overdraw and vertex count per blade, and the cutout technique (alpha test, alpha-to-coverage or alpha hash) has to be chosen together with the anti-aliasing method.

### Cited Findings

Measured and documented scale
- [MEASURED] One 6,056-triangle plant via `InstancedMesh`, three 0.186.1, RTX 5070 Ti, 1280×720, DPR 1, no AA: 1k and 10k instances hold 59.99 FPS (frame-capped), 100k instances (about 605.6M triangles) runs at 20.26 FPS on classic WebGL; the author calls 100k "a stress fixture, not a production budget" — [three.js forum, 22 Oct 2026](https://discourse.threejs.org/t/three-js-plant-instancing-benchmark-240-desktop-samples-csv-json-and-a-standalone-harness/95719)
- [DOC] `webgl_batch_lod_bvh` at r187: "BatchedMesh with 10 geometries and 500k instances"; LODs from `simplifyGeometriesByErrorLOD( geometries, 4, performanceRangeLOD )` (four simplified levels per geometry) registered with screen-height thresholds — `addGeometryLOD( id, lod1, 0.08 )` "used when below ~8% of the screen height", then 0.04, 0.033, 0.02; `batchedMesh.computeBVH( THREE.WebGLCoordinateSystem )` for culling and `computeBoundsTree()` for raycasts; `customSort = createRadixSort( batchedMesh )`. Libraries: `@three.ez/batched-mesh-extensions` 0.0.11, `@three.ez/simplify-geometry` 0.0.1, `three-mesh-bvh` 0.9.10, `meshoptimizer` 1.1.1. No shadows in the example, no FPS stated — [webgl_batch_lod_bvh source](https://raw.githubusercontent.com/mrdoob/three.js/r187/examples/webgl_batch_lod_bvh.html)
- `InstancedMesh2` (`@three.ez/instanced-mesh`, npm 0.3.16, MIT, 488 stars): per-instance frustum culling (`perObjectFrustumCulled` true by default), optional BVH via `computeBVH({ margin })` that "works very well if the instances are mostly static", `addLOD( geometry, material, distance )`, `addShadowLOD( geometry, distance )`, per-instance visibility/opacity/uniforms, `sortObjects` with `createRadixSort`; demos titled "1kk static trees" and "Skinning 3k instances"; no benchmark figures on the page — [instanced-mesh](https://github.com/agargaro/instanced-mesh), [npm registry](https://registry.npmjs.org/@three.ez/instanced-mesh)

Grass recipes
- [DOC] James Smyth (23 Aug 2021), three.js with custom GLSL: 5 vertices per blade ("The low number of vertices would improve performance and allow more grass to render"); vertex colours mark height ("bottom 2 vertices as black, middle as gray and the top one as white") so sway scales with height; wind is a `sin` of time plus the blade's UV so "blades move at different times, like gusts"; one colour per blade sampled from a splattered green texture by the blade's normalised position; a "black and white cloud noise texture" fakes cloud shadows; source in `James-Smyth/three-grass-demo` — [Smyth Design blog](https://smythdesign.com/blog/stylized-grass-webgl/)
- [DOC] `simondevyoutube/Quick_Grass` (MIT, 233 stars): three.js source for "How do Major Video Games Render Grass?", described as based on the Ghost of Tsushima GDC talk; the repository page gives no counts or timings — [Quick_Grass](https://github.com/simondevyoutube/Quick_Grass)
- [MEASURED] A grass system's WebGL version ran at "around 40 fps at 1440p" on an M1 Mac; its WebGPU rewrite reached "locked 60fps at 1440p on a M1 Mac with both grass types" (23 Jul 2026) using tiling, cross-faded LOD, per-blade frustum culling "to reduce fragment shader work", interaction with up to 8 objects, and an alternate billboard grass type "for denser vegetation at lower cost"; closed source — [three.js forum, Jul–Oct 2026](https://discourse.threejs.org/t/migrating-my-grass-system-to-webgpu-and-making-a-robust-grass-plugin/92893)

Cutout and transparency options
- `alphaHash`: "an alternative to Material#transparent or Material#alphaTest. The material will not be rendered if opacity is lower than a random threshold. Randomization introduces some grain or noise, but approximates alpha blending without the associated problems of sorting. Using TAA can reduce the resulting noise." — [Material docs](https://threejs.org/docs/pages/Material.html)
- `alphaToCoverage`: "Can only be used with MSAA-enabled contexts (meaning when the renderer was created with antialias parameter set to `true`). Enabling this will smooth aliasing on clip plane edges and alphaTest-clipped edges." — [Material docs](https://threejs.org/docs/pages/Material.html)
- `forceSinglePass`: double-sided transparent objects are drawn with two draw calls by default; "There are scenarios however where this approach produces no quality gains but still doubles draw calls e.g. when rendering flat vegetation like grass sprites. In these cases, set the `forceSinglePass` flag to `true`" — [Material docs](https://threejs.org/docs/pages/Material.html)
- Examples: `webgl_materials_alphahash`, `webgl_instancing_scatter`, `webgl_buffergeometry_instancing_billboards`, `webgl_lod` — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)
- MSAA availability: `MAX_SAMPLES` ≥4 on 100% of surveyed WebGL 2 devices, ≥8 on 64% — [Web3D Survey: WebGL 2](https://web3dsurvey.com/webgl2)

### Inferences
- Scaling the one hard number down: the RTX 5070 Ti handled roughly 60M triangles per frame at 60 FPS (10k plants) with headroom unknown because of the frame cap. An integrated GPU is one to two orders of magnitude weaker and far more fill-rate-limited, so a prudent starting budget is a few hundred thousand vegetation triangles on screen, with distant vegetation as cards or baked into the terrain colour. This is my extrapolation, not a measurement.
- Recipe for map-scale forests: one `InstancedMesh` per tree species of 100–300-triangle "clump" meshes (not individual trees), instance matrices written once, wind in the vertex shader. Beyond a camera distance, drop to crossed quads or let the terrain shader's forest tint take over. Impostors (earlier notes) are unnecessary below about 10k trees.
- Recipe for close-up grass and reeds (city diorama edges, duel ground, river banks): 5–7 vertex blades, opaque geometry (no alpha at all), per-instance position/rotation/height/phase attributes, height-weighted sway driven by a scrolling world-space noise so gusts travel across the field, colour from a low-frequency ground tint texture, normals bent towards up so lighting stays soft. Opaque blades avoid the cutout problem entirely and are the cheapest fill-rate choice.
- Wind should be one global system: a 2D scrolling noise texture (or a couple of summed sines) in world space sampled by grass, trees, banners, cloth, smoke drift and water streaks, so everything gusts together. This coherence is more noticeable than any single asset's fidelity.
- Choosing the cutout mode for leaf cards and thatch: with the MSAA canvas or an MSAA composer target, `alphaTest` + `alphaToCoverage` gives clean edges cheaply; if AO forces MSAA off (section 4), fall back to plain `alphaTest` with slightly inflated alpha in distant mips and SMAA; `alphaHash` is only attractive with temporal accumulation, which WebGLRenderer has only for still frames (`TAARenderPass`), so its grain would show in motion — although film grain in the grading pass can make that grain acceptable in a low-key look.
- Set `forceSinglePass = true` and `side: DoubleSide` on vegetation cards to avoid the doubled draw calls, and give instanced fields explicit bounding spheres so they are not culled as one object.
- Vegetation in shadow passes is where triangle counts double: use a much simpler shadow proxy (the `addShadowLOD` idea) or exclude grass from shadow casting altogether.

### Gaps
- No WebGL grass benchmark with blade counts and frame times on any GPU, and no vegetation measurement on an integrated GPU, was found (search budget exhausted).
- The WebGL internals of the grass system that later migrated to WebGPU are not described in its thread.
- No frame-time comparison of `alphaTest` vs `alphaToCoverage` vs `alphaHash` was found.

## 9. Atmosphere: height fog, volumetric light shafts, dust motes, rain and snow, GPU particle systems, soft and lit particles

### Takeaway
Analytic height fog costs one extra exponential and a division per pixel and is the highest-value atmospheric effect for a misty look; light shafts have two documented WebGL routes — a cheap radial blur at half resolution (pmndrs `GodRaysEffect`, 60 samples) and true shadow-map ray-marching (`three-good-godrays`, 60 steps, now used by three.js's own WebGL example) — while GPU-compute particles are WebGPU-only and `three.quarks` remains the maintained batched CPU particle system for WebGL.

### Cited Findings

Fog
- [DOC, non-three.js] Inigo Quilez's fog article: basic `float fogAmount = 1.0 - exp(-t*b);`; sun-tinted fog `float sunAmount = max( dot(rd, lig), 0.0 );` with the fog colour mixed from bluish to yellowish by `pow(sunAmount,8.0)`; separate extinction and in-scattering `finalColor = pixelColor*(1.0-extColor) + fogColor*insColor;`; and analytic height fog for density `a·e^(−b·y)`: `float fogAmount = (a/b) * exp(-ro.y*b) * (1.0-exp(-t*rd.y*b))/rd.y;` — "the only extra cost over the constant-density version is one division" — [iquilezles.org: fog](https://iquilezles.org/articles/fog/)
- three.js has height-fog and scattering-fog examples only on the node stack (`webgpu_fog_height`, `webgpu_custom_fog`, `webgpu_custom_fog_scattering`, `webgpu_postprocessing_fog`) — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)
- A fog-colour trick from a shipped PlayCanvas game: the fog colour "is sampled from the bottom of the mountain painting so the slope, haze, and peaks blend together" — [PlayCanvas blog, 9 Nov 2026](https://blog.playcanvas.com/building-mojo-ski-300m-views-in-seven-hours)

Light shafts
- [DOC] pmndrs `GodRaysEffect( camera, lightSource, options )`: defaults `samples` 60, `density` 0.96, `decay` 0.9, `weight` 0.4, `exposure` 0.6, `clampMax` 1.0, `resolutionScale` 0.5, `kernelSize` SMALL, `blur` true; the light source must be a Mesh or Points that "Must not write depth and has to be flagged as transparent"; "A higher sample count improves quality at the cost of performance" — [postprocessing docs: GodRaysEffect](https://pmndrs.github.io/postprocessing/public/docs/class/src/effects/GodRaysEffect.js~GodRaysEffect.html)
- [DOC] `three-good-godrays` (239 stars; 0.12.2 on 5 Nov 2026): "raymarching through the scene and sampling the shadow map to determine which points are in shadow"; supports `PointLight` or `DirectionalLight`; defaults `raymarchSteps` 60, `density` 1/128, `maxDensity` 0.5, `distanceAttenuation` 2, `edgeStrength` 2, `edgeRadius` 2, `blur` true; needs shadow maps enabled and the pmndrs `postprocessing` composer; tested with `three >= 0.125.0 < 0.188.0` — [three-good-godrays](https://github.com/Ameobea/three-good-godrays), [npm registry](https://registry.npmjs.org/three-good-godrays)
- The official `webgl_postprocessing_godrays` example at r187 loads `three-good-godrays@0.12.0` from a CDN and builds `new EffectComposer( renderer, { frameBufferType: THREE.HalfFloatType } )` with a `GodraysPass( pointLight, camera, params )` using the defaults above — [webgl_postprocessing_godrays source at r187](https://raw.githubusercontent.com/mrdoob/three.js/r187/examples/webgl_postprocessing_godrays.html)
- [DOC] Maxime Heckel, 10 Jun 2025 (R3F + pmndrs `Effect`, WebGL GLSL): ray-march from the camera in a post effect, reconstructing world position from depth with `projectionMatrixInverse` and `viewMatrixInverse`; first version `NUM_STEPS` 250 at `STEP_SIZE` 0.05, optimised to 50 steps at 0.5 with a blue-noise offset of the ray start (`gl_FragCoord.xy / 1024.0`, cycled per frame with `frame%32`) to remove banding; light shaped by an SDF cone with a 0.1 smooth edge; Henyey-Greenstein phase; Beer's law; shadowing from a dedicated 256²–512² `DepthTexture` rendered from the light; FBM noise density (frequency 0.5, 3 octaves). Caveats: each light needs its own camera, FBO and shadow test; the cube-map variant is "at best, a cool hack"; no frame times given — [Maxime Heckel: On Shaping Light](https://blog.maximeheckel.com/posts/shaping-light-volumetric-lighting-with-post-processing-and-raymarching/)
- A shipped r186 game lists "HDR pipeline, sun shafts, bloom, ACES, a colour grade with canvas grain" as its look — [three.js forum, Nov 2026](https://discourse.threejs.org/t/tides-of-fortune-an-open-world-pirate-game-in-three-js-with-zero-asset-files/96867)

Particles
- `three.quarks` (1.3k stars, MIT, npm 0.18.0): batched renderer; billboard, stretched-billboard, mesh and trail modes; lit particles "with MeshStandardMaterial and MeshPhysicalMaterial, including env maps"; sprite sheets with frame blending; emitter shapes point/sphere/hemisphere/cone/circle/mesh surface/grid; "each sprite batch uploads one interleaved buffer per frame (48–64 bytes per particle)"; WebGL soft particles "needs a depth pre-pass + `setDepthTexture`"; a `three.quarks/webgpu` entry built on TSL — [three.quarks](https://github.com/Alchemist0823/three.quarks), [npm registry](https://registry.npmjs.org/three.quarks)
- `three-nebula` (1.3k stars, MIT, 33 open issues): "built and tested against three@0.185.1"; `SpriteRenderer` and `MeshRenderer` on WebGL; the batched single-draw-call `GPURenderer` is at the `three-nebula/webgpu` entry point for `WebGPURenderer` — [three-nebula](https://github.com/creativelifeform/three-nebula)
- Compute-shader particles (`webgpu_compute_particles`, `_particles_rain`, `_particles_snow`, `_particles_fluid`) and soft particles (`webgpu_particles_soft`) are `webgpu_*` examples; the WebGL GPGPU route is the render-target ping-pong shown in `webgl_gpgpu_birds`, `webgl_gpgpu_protoplanet` and `webgl_gpgpu_water`; plain attribute-driven points are in `webgl_buffergeometry_custom_attributes_particles` and `webgl_points_sprites` — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)
- EXT_color_buffer_float (needed for float simulation targets) is supported by 99.95% of surveyed WebGL 2 devices; EXT_color_buffer_half_float 91.51%; EXT_float_blend 93.89% — [Web3D Survey: WebGL 2](https://web3dsurvey.com/webgl2)

### Inferences
- Height fog recipe for all four scenes (untested): add iq's height-fog term to every material's fog stage — for built-in materials by replacing the `fog_fragment` chunk through `onBeforeCompile`, for custom `ShaderMaterial`s as a shared GLSL include — with density falling off with world height so valleys, rivers and the base of walls sit in mist while ridges and roofs clear it. Tint the fog towards the bronze-gold key light by `pow( max( dot( viewDir, lightDir ), 0. ), 8. )` for the warm glow around a low sun or a fire, and keep extinction and in-scatter colours separate so distant objects drain towards the palette's grey-blue. Cost: one `exp`, one division, one `pow`, no fetches.
- Animated mist: multiply the fog density by a low-frequency 3D-ish noise (two scrolling 2D fetches) evaluated at the fragment's world position; cheap, and it reads as drifting banks on the map. True ray-marched volumetric fog is a high-tier-only luxury.
- Light shafts, tiered: (low) none, rely on sun-tinted fog; (medium) radial blur — render a small occlusion mask of bright sky/fire against black silhouettes at half or quarter resolution and blur it radially from the light's screen position with 30–60 taps, additive, which only works while the light is on or near the screen; (high, set-piece) shadow-map ray-march at half resolution with 16–32 steps and blue-noise offset, composited with a depth-aware upsample. The documented 60-step defaults at full resolution are too heavy for integrated GPUs; halving resolution quarters the pixel count and blue noise lets the step count drop, per Heckel's 250 → 50 result.
- `three-good-godrays` requires the pmndrs composer and is pinned below r188, and with the default `PCFShadowMap` it copies the shadow depth every frame; for a project on three's own EffectComposer it is better used as a reference implementation for a custom pass than as a dependency.
- Dust motes and embers: a few hundred to a few thousand instanced quads or `Points` with all motion computed in the vertex shader from a per-particle seed and time (stateless: position = seed-based start + drift + curl-like sine offsets, wrapped inside a camera-centred box). Zero per-frame CPU upload, one draw call. Light them by sampling the key-light colour and shadow term at low cost, or simply modulate by a "beam" mask so motes sparkle only inside light shafts — that pairing sells volumetric light better than either effect alone.
- Rain and snow: the same stateless wrap-around box, with stretched quads aligned to the fall direction for rain. Thousands of particles need no GPGPU. Reserve `three.quarks` for authored bursts (dust kicked by hooves, sparks from clashing weapons, smoke plumes) where emitter shapes, sub-emitters and sprite-sheet animation save authoring time; its per-frame upload of 48–64 bytes per particle makes a few thousand live particles a few hundred kilobytes per frame, fine on any GPU.
- Soft particles need scene depth; if a depth texture is already produced for AO or fog post effects, reuse it for smoke and mist sprites, otherwise fake softness by fading particles near the ground plane analytically (height above terrain) — on a heightmap terrain that needs no depth buffer.
- Lit smoke for firelight: per-particle lighting from the nearest fire as a simple distance falloff tint gives the warm underlit smoke of the art direction far more cheaply than `MeshStandardMaterial` particles.

### Gaps
- No frame-time measurements for any light-shaft method or for `three.quarks` on any GPU were found.
- No WebGL three.js example of height fog exists in the repo; the chunk-replacement recipe is inference.
- Maintenance recency of `three-nebula` (last commit date) was not visible on the page read.
- The earlier notes' statement that pmndrs has a `GodRaysEffect` is confirmed; whether the pmndrs effect's internals are a radial blur of an occlusion mask is not stated on the docs page read (that description is from general knowledge).

## 10. Crowds and animation: InstancedMesh with vertex-animation textures or instanced skinning, BatchedMesh, level of detail, and the cost of skinned characters with AnimationMixer

### Takeaway
Individually skinned characters hit a CPU wall, not a GPU one: on an older gaming-laptop CPU (Intel Core i7-4720HQ), 25-bone, 900-triangle units dropped below 60 FPS past about 200 with one `AnimationMixer` each, while sharing skeletons per animation state reached 1,000 at 60 FPS; the documented WebGL crowd routes that avoid skeletons are per-instance morph targets (`webgl_instancing_morph`, 1,024 animated horses in one draw call) and rigid-part instancing, with true instanced skinning officially demonstrated only on WebGPU and available on WebGL through `InstancedMesh2`.

### Cited Findings
- [MEASURED] Forum thread (Nov–Dec 2023; Intel Core i7-4720HQ laptop; model 700 vertices, 900 triangles, 25 bones; `SkeletonUtils.clone()` and one `AnimationMixer` per unit): frames fell below 60 FPS beyond about 200 skinned meshes with no shadows; 300 units means 7,500 bone `Object3D`s updated per frame; about 75% of scene CPU time was `AnimationMixer.update()`, `updateMatrixWorld()` on bones, and `projectObject()`/`Skeleton.update()`; "the bottleneck turned out to be CPU calculations (not rendering)" — [three.js forum](https://discourse.threejs.org/t/optimization-of-large-amounts-100-1000-of-skinned-meshes-cpu-bottlenecks/58196)
- [MEASURED] Same thread, results by technique: throttling animation to every Nth frame (with `bindMode = "detached"` so matrices, skeleton and mixer are throttled together) gave 500 units at 60 FPS, N=4 acceptable, N=12 choppy; sharing one skeleton per animation state gave 1,000 animated skinned meshes at 60 FPS on the same laptop without throttling, after which "the bottleneck moved to draw calls"; an instanced-skinning implementation with throttling went "from 10 fps with 2,000 instances to 144 fps" (different author and machine); an unoptimised instanced demo with 2,000 skinned meshes ran at about 5 FPS in Firefox and 10 in Chrome. CodyJasonBennett: "Skinning is done on the GPU with a bone texture in all cases; that's not the problem." — [three.js forum](https://discourse.threejs.org/t/optimization-of-large-amounts-100-1000-of-skinned-meshes-cpu-bottlenecks/58196)
- [DOC] `webgl_instancing_morph` at r187: `new THREE.InstancedMesh( dummy.geometry, dummy.material, 1024 )` horses on a 32 × 32 grid; one shared `AnimationMixer`; each frame, for every instance, `mixer.setTime( time + timeOffsets[ i ] ); mesh.setMorphAt( i, dummy );` then `mesh.morphTexture.needsUpdate = true` once; instance matrices are written once; shadows on with a 2048 `SunLight` map — [webgl_instancing_morph source](https://raw.githubusercontent.com/mrdoob/three.js/r187/examples/webgl_instancing_morph.html)
- `InstancedMesh2` skinning API: `initSkeleton( skeleton )`, then `mixer.update( time )` and `setBonesAt( index )` per instance; demo "Skinning 3k instances"; how bone data is stored and its CPU cost are not stated — [instanced-mesh](https://github.com/agargaro/instanced-mesh)
- Official instanced-skinning examples exist only for the node renderer: `webgpu_skinning_instancing`, `webgpu_skinning_instancing_individual`; on WebGL there is `webgl_tsl_skinning` through the compatibility layer, where "Sharing NodeMaterials between SkinnedMeshes" is unsupported — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json), [PR #32851](https://github.com/mrdoob/three.js/pull/32851)
- `BatchedMesh` developments: per-instance opacity (r183), sort-corruption and matrix-leak fixes (r187), and the `webgl_batch_lod_bvh` pattern of per-geometry LOD by screen height (section 8) — [r183 notes](https://github.com/mrdoob/three.js/releases/tag/r183), [r187 notes](https://github.com/mrdoob/three.js/releases/tag/r187), [webgl_batch_lod_bvh source](https://raw.githubusercontent.com/mrdoob/three.js/r187/examples/webgl_batch_lod_bvh.html)
- [RULE] PlayCanvas: for skinned meshes, "setting up a custom AABB for the character" avoids per-frame bounds recalculation — [PlayCanvas optimization guidelines](https://developer.playcanvas.com/user-manual/optimization/guidelines/)
- LOD in a shipped r186 game: "27 types built from 6 parametric hull designs," with "a lighter hull beyond ~200 m" and a lighter level of detail beyond about 1 km — [three.js forum, Nov 2026](https://discourse.threejs.org/t/tides-of-fortune-an-open-world-pirate-game-in-three-js-with-zero-asset-files/96867)

### Inferences
- For a project whose characters are procedural geometry, skeletons are optional. The cheapest convincing army is rigid-part instancing: one `InstancedMesh` per part type (torso+head, shield, spear, horse body, four leg segments, banner pole), with gait produced in the vertex shader from a per-instance phase attribute — legs swing by rotating around a pivot encoded in a vertex attribute, torsos bob at twice the stride frequency. Per-frame CPU cost is zero when the formation moves as a block (animate a formation offset uniform), or one `instanceMatrix` upload when soldiers move individually. A war theater of two armies of 500 soldiers each is then about ten draw calls.
- The documented morph route fits richer silhouettes: build 6–8 key poses of a soldier or horse procedurally as morph targets, and blend per instance. The official example's per-frame loop (1,024 mixer evaluations plus a full morph-texture upload) can be replaced by writing two weights per instance from a phase, which removes the mixer entirely.
- A vertex-animation texture is the same idea taken further (positions per vertex per frame in a float texture, sampled in the vertex shader by `frame` and vertex index). No maintained three.js VAT library was verified in this or the earlier session; for procedural characters with a handful of looping poses, morph targets cover the need without building that pipeline.
- If rigged glTF characters are ever introduced for the duel, two fully skinned characters with one mixer each are far below the measured ~200-unit CPU wall; the wall only matters for crowds. For crowds of rigged characters the measured ordering of fixes is: share skeletons per animation state (5× on the cited laptop), then throttle updates, then instanced skinning (`InstancedMesh2`).
- LOD policy by screen size rather than distance (as in `webgl_batch_lod_bvh`) suits a zooming strategy camera: full soldiers when a figure exceeds about 8% of screen height, simplified figures below that, and a textured formation card or instanced billboards below about 2%.
- Shadow cost doubles crowd vertex work; give armies a shadow proxy (one box or capsule per soldier in a separate instanced mesh that only casts) or blob shadows.

### Gaps
- No published benchmark for `InstancedMesh2` skinning or for per-instance morph crowds on any GPU was found; the "3k instances" figure is a demo title.
- No maintained, documented vertex-animation-texture library for three.js was verified (search budget exhausted).
- The skinned-mesh measurements are from 2023 on r158-era three.js and an old CPU; no 2026 re-measurement was found.

## 11. Cloth, banners, capes, tassels, manes: vertex-shader animation and simple CPU verlet simulation

### Takeaway
The only official cloth simulation left in three.js that is not a physics-engine demo is `webgpu_compute_cloth`, which requires the WebGPU backend, but its design — a 31 × 31 verlet grid with structural and shear springs, 360 fixed steps per second and a sheen material — is small enough to run on the CPU for a handful of hero cloths; everything else (many banners, manes, tassels) is better done as stateless vertex-shader motion.

### Cited Findings
- [DOC] `webgpu_compute_cloth` at r187: `clothNumSegmentsX = 30`, `clothNumSegmentsY = 30` (961 verlet vertices over a 1 × 1 area); springs to left and upper neighbours (structural) and both diagonals (shear), bend springs present but commented out; seven top-row vertices pinned; `stiffnessUniform = 0.2` (GUI 0.1–0.5), `dampeningUniform = 0.99`, gravity `0.00005` per step, wind from `triNoise3D` scaled by `0.0001`; `stepsPerSecond = 360` with a fixed-timestep accumulator and frame delta clamped to 1/60 s; sphere collision pushes vertices out along the normal; normals rebuilt from tangent/bitangent cross products; material `MeshPhysicalNodeMaterial`, `DoubleSide`, sheen 1.0, sheen roughness 0.5, opacity 0.85 — [webgpu_compute_cloth source at r187](https://raw.githubusercontent.com/mrdoob/three.js/r187/examples/webgpu_compute_cloth.html)
- The same example requires WebGPU (`WebGPU.isAvailable()` check, `requiredLimits: { maxStorageBuffersInVertexStage: 1 }`) and carries the note "TODO: Fix example with WebGL backend" — [webgpu_compute_cloth source at r187](https://raw.githubusercontent.com/mrdoob/three.js/r187/examples/webgpu_compute_cloth.html)
- The examples index has `physics_ammo_cloth` and `physics_ammo_rope` (Ammo.js soft bodies) but no `webgl_animation_cloth` — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)
- Height-weighted vertex-shader sway, documented for grass and directly reusable for cloth strips: vertex colours mark how far each vertex is from the anchor so "The bottom vertices were kept static," the middle moves a little and the top moves most, with a `sin` of time plus a per-object phase — [Smyth Design blog](https://smythdesign.com/blog/stylized-grass-webgl/)
- `sheen` is documented as "Used for cloth and fabric"; `forceSinglePass` avoids doubled draw calls on double-sided transparent cards — [MeshPhysicalMaterial docs](https://threejs.org/docs/pages/MeshPhysicalMaterial.html), [Material docs](https://threejs.org/docs/pages/Material.html)

### Inferences
- Vertex-shader banner recipe (untested, standard practice): give each banner vertex a `pin` weight (0 at the pole edge, 1 at the free edge, squared for a natural falloff). Displace along the banner normal by two or three travelling sine waves whose phase advances with distance from the pole and with time scaled by the global wind strength, add a slower large-amplitude swing and a slight droop proportional to `pin` when wind is low, then recompute the normal analytically from the wave derivatives (or with two offset evaluations) so the sheen highlight ripples. One draw call can carry every banner in an army if phase, colour and emblem-atlas index are per-instance attributes. Cost: a few dozen vertex instructions, no CPU work.
- The same pin-weighted approach covers manes and tails (strips of 4–6 segments with the weight growing along the strip, driven by the horse's velocity and the gait phase), tassels (short strips or a single swinging quad), and capes at a distance. Adding a term proportional to the rider's acceleration, low-pass filtered on the CPU and passed as a uniform, gives the "follow-through" that makes a charge read as fast.
- CPU verlet for the duel's hero cloth (two capes, perhaps two banners): 12 × 16 particles per cape with structural and shear constraints, 2–4 relaxation iterations, two or three sub-steps per frame, and collision against two or three capsules (torso, horse back, saddle). That is under 200 particles and about 700 constraints per cloth — tens of microseconds of arithmetic per frame in JavaScript — followed by one position-buffer upload and a normal recompute. The official example's constants (stiffness 0.2, damping 0.99, 360 steps/s) are a tuning starting point, though a CPU version would usually use position-based constraints rather than the example's force accumulation.
- Simulated cloth must be decoupled from frame rate (fixed timestep with clamped delta, as the example does), or capes explode after a tab switch or a slow frame.
- Choose by camera distance: verlet only when a cape fills a meaningful part of the screen (duel close-ups), vertex-shader waves everywhere else. A cross-fade is unnecessary if the two are never used on the same asset in the same scene.

### Gaps
- No maintained WebGL (non-compute) cloth example exists in three.js r187, and no current three.js verlet-cloth tutorial was retrieved (search budget exhausted); the CPU recipe and its cost estimate are inference.
- No measured CPU cost for JavaScript verlet cloth at these sizes was found.

## 12. Decals and ground detail: footprints, scorch marks, blood, tracks

### Takeaway
`DecalGeometry` is the documented way to project a mark onto arbitrary geometry but costs one mesh and one draw call per decal and distorts around corners; for marks on terrain — tracks, hoof prints, scorch, blood, trampled ground behind armies — the scalable approach is to paint into a persistent render-target texture in ground space and sample it in the terrain shader, which is how shipped three.js games draw wakes and trails.

### Cited Findings
- [DOC] `DecalGeometry( mesh, position, orientation, size )` from `three/addons/geometries/DecalGeometry.js`: "create a decal mesh that serves different kinds of purposes e.g. adding unique details to models, performing dynamic visual environmental changes or covering seams"; limitation: "decal projections can be distorted when used around corners" (GitHub issue #21187) — [DecalGeometry docs](https://threejs.org/docs/pages/DecalGeometry.html)
- [DOC] `webgl_decals` at r187 uses a `MeshPhongMaterial` with `map`, `normalMap`, `transparent: true`, `depthTest: true`, `depthWrite: false`, `polygonOffset: true`, `polygonOffsetFactor: - 4`; each click creates `new THREE.Mesh( new DecalGeometry( mesh, position, orientation, size ), material )` with a cloned material, position from the ray hit and orientation from the surface normal; its `removeDecals()` detaches meshes without calling `dispose()` — [webgl_decals source at r187](https://raw.githubusercontent.com/mrdoob/three.js/r187/examples/webgl_decals.html)
- `polygonOffset` docs: "Can be useful for rendering hidden-line images, for applying decals to surfaces, and for rendering solids with highlighted edges." EXT_polygon_offset_clamp is available on 92.94% of surveyed WebGL 2 devices — [Material docs](https://threejs.org/docs/pages/Material.html), [Web3D Survey: WebGL 2](https://web3dsurvey.com/webgl2)
- Render-to-texture trails in a shipped r186 game: "foam wakes drawn into a texture" — [three.js forum, Nov 2026](https://discourse.threejs.org/t/tides-of-fortune-an-open-world-pirate-game-in-three-js-with-zero-asset-files/96867)
- Particle trails in another 2026 game: the tyre trail is made of square particles the author chose to keep — [three.js forum, Jul 2026](https://discourse.threejs.org/t/infinite-procedural-post-apocalyptic-winter-driving-game/93196)
- (From the earlier notes) Bruno Simon's Folio 2025 game loop lists "tracks and trails" among its systems — [folio-2025 README](https://github.com/brunosimon/folio-2025)

### Inferences
- Ground-space "detail map" recipe (untested; generalises the cited wake technique): keep one render target per scene covering the playable ground (for example 1024² RGBA8 for a duel arena, 2048² for the campaign map), with channels assigned to trample/mud, scorch, blood and wetness. Each frame, draw small instanced brush quads into it with an orthographic top-down camera at the positions where things happen (hoof strikes, marching columns, fires, kills), using additive or max blending; optionally run a slow fade pass so tracks heal. The terrain shader samples the map by world XZ and uses it to darken albedo, raise or lower roughness (wet blood and mud are glossy, scorch is matte), flatten the detail normal, and suppress grass instances. Cost per frame: one tiny draw into the target plus one extra fetch in the terrain shader; the number of marks is unlimited.
- Marching armies on the campaign map leaving a darkened, trampled road behind them, and battlefields that stay scarred after a fight, are cheap with this map and add the kind of persistent detail that reads as "simulation" rather than decoration.
- Use real mesh decals only where the surface is not the ground: arrows stuck in shields, blood on a wall, damage on a gate. Cap the count with a ring buffer, share one material (do not clone per decal as the example does), dispose geometries on eviction, and merge static decals into one geometry so they cost one draw call.
- Flat quad decals on near-flat ground (blob shadows, selection rings, footprints in the duel) are cheaper than `DecalGeometry`: instanced quads aligned to the terrain normal with `polygonOffset`, `depthWrite: false` and `transparent: true`, exactly the material settings of the official example.
- Depth-projected ("deferred") decals, which reconstruct position from the depth buffer inside a box volume, need the scene depth texture and cannot easily modify roughness or normals in a forward renderer; with heightmap terrain the ground-space map achieves the same result with less machinery.

### Gaps
- No three.js write-up of a persistent ground-space trail or track texture with implementation detail was retrieved (the cited game mentions it in one line); the recipe is inference.
- No maintained three.js projected-decal library for WebGL was verified (search budget exhausted); drei's `Decal` component was not read.

## 13. Post-processing and anti-aliasing: pmndrs versus three's addons, TAA/TRAA, SMAA, FXAA, MSAA, bloom, depth of field, motion blur, LUTs, film grain, sharpening, tone mapping

### Takeaway
On WebGLRenderer the anti-aliasing choices are MSAA, SMAA or FXAA — `TAARenderPass` only accumulates on still frames and true temporal AA (TRAA), TAA upscaling, FSR1 and motion blur exist only as `webgpu_*` examples — and bloom is the one effect with a published cost: after the r186 optimisation its ten blur passes take 0.53 ms at 1080p on an Apple M1. pmndrs `postprocessing` still merges effects into fewer passes but is capped at r187 and has no stable v7.

### Cited Findings

Stacks
- pmndrs `postprocessing` (about 3.0k stars, Zlib): `EffectPass` "automatically organizes and merges any given combination of effects"; uses a single fullscreen triangle; recommended renderer settings `powerPreference: "high-performance"`, `antialias: false`, `stencil: false`, `depth: false`; keep the renderer at `NoToneMapping` and "use a `ToneMappingEffect` at the end of the pipeline"; low-precision buffers "cause banding in dark scenes", `HalfFloatType` is "the preferred option for HDR-like workflows on desktop devices" — [postprocessing README](https://github.com/pmndrs/postprocessing)
- pmndrs versions: v6.39.6 (1 Nov) `three ≥0.168.0 <0.188.0`; v6.39.5 added an "EffectComposer multisampling fallback"; v7 only as betas — [postprocessing releases](https://github.com/pmndrs/postprocessing/releases)
- three `EffectComposer`: "Post-processing passes are executed in order of their addition/insertion. The last pass is automatically rendered to screen."; WebGLRenderer only; constructor `( renderer, renderTarget )` where "This render target and a clone will be used as the internal read and write buffers. If not given, the composer creates the buffers automatically." — [EffectComposer docs](https://threejs.org/docs/pages/EffectComposer.html)
- Built-in `setEffects()` path: experimental in its author's words, with a noted double-pass cost (section 1) — [PR #32461](https://github.com/mrdoob/three.js/pull/32461)

Anti-aliasing
- `TAARenderPass`: "When there is no motion in the scene, the TAA render pass accumulates jittered camera samples across frames to create a high quality anti-aliased result. Note: This effect uses no reprojection so it is no TRAA implementation."; `accumulate` defaults to false; extends `SSAARenderPass` — [TAARenderPass docs](https://threejs.org/docs/pages/TAARenderPass.html)
- WebGL examples: `webgl_postprocessing_taa`, `webgl_postprocessing_smaa`, `webgl_postprocessing_fxaa`, `webgl_postprocessing_ssaa`, `webgl_multisampled_renderbuffers`. WebGPU-only: `webgpu_postprocessing_traa`, `webgpu_upscaling_taau`, `webgpu_upscaling_fsr1`, `webgpu_postprocessing_motion_blur` — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)
- MSAA sample support: `MAX_SAMPLES` ≥4 on 100% of surveyed devices, ≥8 on 64%, ≥16 on 20% — [Web3D Survey: WebGL 2](https://web3dsurvey.com/webgl2)
- "Hardware antialiasing does not work with AO. SMAA is recommended." — [N8AO README](https://github.com/N8python/n8ao)
- Field choice in a shipped r186 game: FXAA by default, SMAA + GTAO at "Ultra"; a later pipeline rework gave "17 to 31% less frame time (on my setup, at least), same picture" — [three.js forum, Nov 2026](https://discourse.threejs.org/t/tides-of-fortune-an-open-world-pirate-game-in-three-js-with-zero-asset-files/96867)

Bloom
- [MEASURED] `UnrealBloomPass` after PR #34479 (r186), timed on an Apple M1 with `EXT_disjoint_timer_query_webgl2` around the blur draws: 1920×1080 0.79 → 0.53 ms; 3840×2160 1.32 → 0.82 ms. The pass blurs five mips horizontally and vertically (ten blur passes); taps per pass fell from 11/19/27/35/43 to 7/11/15/19/23 by fetching adjacent taps as one bilinear sample; output differs by "at most 0.4% relative on hard edges" — [PR #34479](https://github.com/mrdoob/three.js/pull/34479)
- r186 also stopped the pass requesting a depth buffer (#34036) — [r186 notes](https://github.com/mrdoob/three.js/releases/tag/r186)

Depth of field, grading, grain, sharpening, tone mapping
- WebGL examples: `webgl_postprocessing_dof`, `webgl_postprocessing_dof2`, `webgl_postprocessing_3dlut`, `webgl_postprocessing_afterimage`, `webgl_postprocessing_unreal_bloom_selective` — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)
- pmndrs effect families: Antialiasing, Bloom, Blur, Color Grading (LUT, brightness/contrast, hue/saturation), Depth of Field, God Rays, Noise, Outline, SSAO, Tone Mapping, Vignette — no motion blur or sharpening listed — [postprocessing README](https://github.com/pmndrs/postprocessing)
- Sharpening/upscaling in three exists only as `webgpu_upscaling_fsr1` — [examples index](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/files.json)
- Grain in practice: "a colour grade with canvas grain" at the end of an HDR chain with ACES — [three.js forum, Nov 2026](https://discourse.threejs.org/t/tides-of-fortune-an-open-world-pirate-game-in-three-js-with-zero-asset-files/96867)
- Tone mapping: r187 "Fix ACES Filmic fit denominator" (#35110) — a small change to ACES output; official examples still pair ACES with `SunLight`/`Sky` (`webgl_lightprobes_sponza`) — [r187 notes](https://github.com/mrdoob/three.js/releases/tag/r187), [webgl_lightprobes_sponza source](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/webgl_lightprobes_sponza.html)

### Inferences
- Anti-aliasing decision for this project: (a) no AO tier → MSAA ×4 on the composer's first render target, which also enables `alphaToCoverage` for foliage and costs little on tile-based and desktop GPUs for modest geometry; (b) AO tier → MSAA off (N8AO's constraint), SMAA last in the chain after tone mapping. FXAA is the fallback for the lowest tier because it is a single cheap pass, at the price of softening fine detail — the opposite of this upgrade's goal, so prefer lowering DPR over FXAA where possible.
- Still-frame super-sampling is free quality for a strategy game: when the camera and scene are idle, accumulate jittered frames (`TAARenderPass` with `accumulate = true`, or a custom accumulation of a few jittered renders) and present the converged image; this also resolves `alphaHash` grain and shadow noise, then switch back to the real-time path on input.
- Motion blur and sharpening have no maintained WebGL implementation in three's addons or pmndrs. Camera-only motion blur can be approximated from depth and the previous view-projection matrix in a custom pass, but for a strategy camera it is low value. A contrast-adaptive sharpen is a 5-tap filter that can be folded into the final grading shader at near-zero extra cost, and is worth having if DPR is reduced on weak GPUs.
- Pass-merging remains the main cost lever on integrated GPUs (as the earlier notes argue). Concretely for the existing chain: fold LUT/grade, vignette, grain, dither, sharpen and the output transform into one `ShaderPass` after bloom, so the full-resolution passes are scene → (AO) → bloom composite → final. The cited game's "17 to 31% less frame time, same picture" from a pipeline rework is the kind of gain to expect, though its details are not published.
- Bloom for a dark, firelit look: because most of the frame is below any reasonable threshold, bloom cost is all overhead on dark pixels; run it from a half-resolution bright-pass and consider three mips instead of five on the low tier. The published 0.53 ms on an M1 suggests low single-digit milliseconds on UHD-class integrated graphics at 1080p (my extrapolation).
- Depth of field: use it as tilt-shift on the diorama and as a shallow-focus accent in the duel, at half resolution, and never while the player is reading the campaign map.
- Tone mapping for low-key scenes (inference, building on the earlier notes): AgX or Neutral keeps bronze-gold highlights from clipping to white and keeps drained colours from shifting hue; whichever is chosen, grade after tone mapping with the LUT so the palette is authored in display space, and apply grain last, after sharpening.

### Gaps
- No published millisecond costs for SMAA, FXAA, MSAA resolve, `BokehPass`/DoF, LUT or grain passes on any GPU were found.
- How to request MSAA on three's own `EffectComposer` (a `WebGLRenderTarget` with `samples`) is not stated on the docs page read; the `webgl_multisampled_renderbuffers` example exists but its source was not fetched.
- The default buffer type of three's `EffectComposer` is not stated on its docs page.
- No maintained WebGL motion-blur or sharpening pass for current three.js was verified.

## 14. Textures and assets: KTX2/Basis, anisotropic filtering, texture arrays, GLTFLoader with meshopt and KTX2

### Takeaway
Nothing fundamental changed since the earlier notes; the additions are that `GLTFLoader` now reads `KHR_meshopt_compression` (r183) and parses embedded KTX2 without a Blob (r187), `KTX2Loader` avoids ETC1 on Chrome with Mesa on Linux (r185), anisotropic filtering is available on 99.47% of WebGL 2 devices, and the 16-sampler limit that every device guarantees makes texture arrays the right container for terrain and atlas layers.

### Inferences
- Anisotropic filtering is the single cheapest detail win for a tilted map and ground planes seen at grazing angles: set `texture.anisotropy = Math.min( 8, renderer.capabilities.getMaxAnisotropy() )` on ground, road, roof and water-normal textures only (not on every texture), and drop to 4 or 2 on the low tier. Without it, procedural ground detail turns to mush a short distance from the camera, which is easily mistaken for missing detail.
- Because this project generates textures in code, most of the KTX2 pipeline is irrelevant to it; the relevant controls are: generate at the smallest size that survives the closest zoom, pack channels (albedo+height, normal+roughness, masks in RGBA), always generate mipmaps for minified surfaces, and put same-size layers in a `DataArrayTexture`. KTX2 only matters for the painted backdrops and any authored tiling textures (earlier notes).
- A procedural-texture cache is worth building: canvas generation at load costs time on every launch; storing generated atlases in IndexedDB (or regenerating from a seed lazily per scene) keeps the first scene fast. This is my inference; no source was consulted.
- Texture memory for the detail upgrade can be budgeted by arithmetic (earlier notes: width × height × 4 × 1.33 bytes uncompressed): four 1024² RGBA arrays of 4 layers each are about 90 MB uncompressed with mips, which is already significant on integrated GPUs that share system RAM; prefer 512² layers with good tiling-break noise over 1024² layers.

## 15. Reference projects 2025–2026 that reach console-like detail in a browser; painterly-plus-PBR examples; Gaussian-splat backdrops

### Takeaway
The best-documented three.js reference for this project's situation is a November 2026 game on r186 that ships entirely procedural content with Gerstner water, an HDR chain with sun shafts, bloom, ACES, grade and grain, FXAA by default and SMAA + GTAO at its top tier; the showcase pieces pushing "realistic" rendering are WebGPU/TSL, other engines (Babylon.js 9.0, PlayCanvas) have moved clustered lighting, volumetric lighting and splats into their cores, and Gaussian-splat backdrops are practical on WebGLRenderer through Spark at about 1–5 million splats on a computer.

### Inferences
- The "Tides of Fortune" stack is close to a template for this project's target: same renderer generation, fully procedural content, a conventional HDR chain, AO only at the top tier, shadow-pass partitioning, LOD by distance, time-sliced generation, and refresh-rate-aware resolution scaling. Nothing in it requires WebGPU. Its lack of published numbers and mixed tester reports also show that such a stack still needs tiering to be safe on weak GPUs.
- "Console-like" claims in 2026 three.js showcases come from WebGPU/TSL projects by specialists (compute rain, SSR/SSGI, TRAA). They are evidence of where the ecosystem's high end is heading, not of what an integrated GPU can run; none publishes frame budgets.
- Feature gaps between WebGLRenderer and peer engines that matter here: clustered many-light shading (Babylon 9, PlayCanvas, and three's node stack with `webgpu_lights_clustered`), which is what would allow dozens of real firelights. On WebGLRenderer, fake most fires: emissive sprites with bloom, a baked probe grid for their bounce, and at most two or three real point lights near the camera.
- Gaussian-splat backdrops are technically practical (Spark runs inside WebGLRenderer and sorts splats with meshes), but a poor fit for this art direction and platform target: splats bake in photographic lighting that will not match a drained, mist-and-firelight grade without heavy colour editing; they need a captured or generated source scene; 1–5 million splats add significant fill and sorting load exactly where integrated GPUs are weakest (the only integrated-class data point is a phone at 38 FPS for 1M splats with nothing else in the scene); and MSAA must be off. A painted or procedurally shaded sky/mountain backdrop with matching fog colour (the "Mojo Ski" trick) gives the layered-depth effect for almost nothing.
- For a painterly-plus-PBR mix, no open-source reference was verified; the closest documented building blocks are the earlier notes' Kuwahara and outline write-ups applied after a physically lit scene. A practical hybrid for this project is to keep PBR lighting response (so firelight, sheen and bronze speculars behave) and stylise in two places only: quantised/painted albedo and roughness textures generated procedurally, and a final grade with paper grain and ink-edge darkening.

## 16. Budgets and measurement for mid-range and integrated GPUs: draw calls, triangles, texture memory, and tools

### Takeaway
There is still no authoritative published budget for integrated GPUs; the usable facts are rules of thumb (100–200 draw calls for low-end mobile, thousands on high-end desktop), a handful of measured costs from fast hardware, and capability-survey floors — so the plan must measure on target hardware, and the tools for that are `renderer.info`, `stats-gl` (CPU and GPU time, where the timer-query extension exists, which is only about 65% of WebGL 2 devices), and manual timer queries around individual passes as three.js's own PRs do.

### Cited Findings

Published budgets and rules
- [RULE] "100-200 draw calls is a rough target for low end mobile devices."; "High end desktop machines on the other hand can process thousands every frame and still maintain 60fps."; "Be careful when enabling 'Use Device Pixel Ratio' … can result in many more pixels being filled, which can cause a significant drop in frame rate"; "Post effects can be expensive so think carefully before you enable them"; "Keep the number of blended mesh instances in your scene to a minimum"; "Keep the number of shaders generated by your app as low as possible"; render on demand for scenes with little visual change — [PlayCanvas optimization guidelines](https://developer.playcanvas.com/user-manual/optimization/guidelines/)
- (Earlier notes) ~100 draw calls on mobile, several hundred to low thousands on desktop, DPR capped at 2 — [Utsubo 100 tips](https://www.utsubo.com/blog/threejs-best-practices-100-tips)

Measured costs collected in this study (all on fast hardware)
- Bloom blur batches: 0.53 ms at 1080p, 0.82 ms at 4K, Apple M1, r186 — [PR #34479](https://github.com/mrdoob/three.js/pull/34479)
- N8AO 2.1 at 1080p, Apple M5 Max: Medium 0.70 ms, Ultra 2.0 ms, half-res upsample ~0.1 ms — [N8AO README](https://github.com/N8python/n8ao)
- Instanced geometry throughput: ~60.6M triangles per frame at a capped 60 FPS and ~605.6M at 20 FPS, RTX 5070 Ti, 720p — [three.js forum, 22 Oct 2026](https://discourse.threejs.org/t/three-js-plant-instancing-benchmark-240-desktop-samples-csv-json-and-a-standalone-harness/95719)
- CPU cost of object count: 4,000 meshes cost 4.5 ms of CPU per render on WebGLRenderer (r183, a laptop with an RTX 4090; CPU model not stated) — [three.js forum, 29 May 2026](https://discourse.threejs.org/t/webgpurenderer-2x-slower-cpu-and-5-10x-slower-first-frame-than-webglrenderer-on-many-mesh-scenes-r183-same-on-both-backends/91904)
- Skinned characters: ~200 individually animated 25-bone units before dropping below 60 FPS on an Intel i7-4720HQ; 1,000 with shared skeletons — [three.js forum](https://discourse.threejs.org/t/optimization-of-large-amounts-100-1000-of-skinned-meshes-cpu-bottlenecks/58196)
- Shadow filter: the r182 PCF rewrite doubled a test scene's frame rate on a Pixel 3a (8 → 18 FPS) — [PR #32303](https://github.com/mrdoob/three.js/pull/32303)
- Gaussian splats on WebGL 2: 1M splats at 38 FPS on an iPhone 13 Pro Max — [PlayCanvas blog, 3 Jun 2026](https://blog.playcanvas.com/new-in-supersplat-webgpu-and-streaming-bring-huge-performance-wins)

### Inferences
- Working budget to start from on an integrated GPU at 1080p, to be corrected by measurement (my synthesis; none of these is a published integrated-GPU number): frame target 16.7 ms with about 10–12 ms for the GPU; DPR 1.0 (1.25 at most); at most 3 full-resolution passes after the scene render; shadow maps totalling no more than one 2048² refreshed per frame; 100–300 draw calls; 200k–500k triangles in view including shadow passes; one screen-space effect (AO *or* light shafts *or* DoF) at half resolution; texture memory under roughly 256 MB because it comes out of shared system RAM.
- Fill rate is the first limit to check, by arithmetic: 1920 × 1080 is 2.07 million pixels; at DPR 2 it is 8.3 million. A chain of scene + bloom composite + grade at DPR 2 fills about 25 million pixels per frame before overdraw; at DPR 1 with half-resolution bloom it fills under 5 million. Any effect whose cost is "taps per pixel" (PCSS at 51, 60-step light shafts, Kuwahara) should be multiplied by that pixel count before being approved for a tier.
- Overdraw from alpha-blended layers (mist cards, smoke, grass cards, water, decals) is the second limit and is invisible in draw-call or triangle counts; measure it by temporarily drawing everything with a constant additive colour, and cap particle size on screen.
- Measurement plan that works without the timer-query extension (about a third of devices lack it): (1) in development, use `stats-gl` with `trackGPU` on Chrome and a per-pass timer-query wrapper to build a cost table per effect per scene; (2) in production, use only frame-time statistics (median and 95th percentile over a 1–2 second window) to drive the tier and DPR controller from the earlier notes; (3) log `renderer.info.render.calls`, `.triangles`, `renderer.info.memory.textures/geometries` and `renderer.info.programs.length` per scene to catch regressions — remembering that with multi-pass rendering `info.autoReset` must be off and reset once per frame. The r185 change that resets the statistics before the shadow-map render probably means shadow-pass draws are now included in a frame's counts; confirm this on r187 before comparing numbers with older builds.
- A/B toggling is the most reliable per-effect cost measure on hardware without timer queries: run a fixed camera path, toggle one effect every N seconds, and compare median frame times with vsync disabled or with the scene scaled until it is clearly GPU-bound (otherwise a 60 Hz cap hides the difference, as the plant benchmark's 1k and 10k rows show).
- Shader count is a budget too: each enabled material lobe, light-count change and `onBeforeCompile` variant is another program to compile at scene entry. Keep `renderer.info.programs.length` in the dozens, pre-warm with `compileAsync` behind transitions (earlier notes), and note that parallel compile is unavailable on about a quarter of devices.
- Linux deserves explicit testing: it has the lowest WebGL 2 availability in the survey, Mesa-specific texture-format workarounds have been needed in `KTX2Loader`, and WebGPU there is limited to recent Intel and NVIDIA-on-Wayland configurations.

### Gaps

- The three.js Inspector docs page returned HTTP 404 at the URL tried; whether the Inspector can profile a WebGLRenderer scene was not confirmed (the earlier notes place it in the node stack).
- Spector.js and browser DevTools GPU profiling were not researched in this session.
- The Web3D Survey page did not state its sampling period or sample size.
